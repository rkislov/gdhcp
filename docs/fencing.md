# Fencing виртуальных и физических узлов

© 2026 Кислов Роман Сергеевич. Apache License 2.0.

Это дополнение к [настройке автоматического кластера](cluster-runtime.md). Fencing гарантирует, что прежний активный узел больше не обслуживает DHCP/API и не обновляет DNS, прежде чем новый узел получит service IP. Для виртуальных машин используйте принудительное выключение через гипервизор, для физических серверов — BMC или управляемое питание.

В текущих исходниках доступны готовые адаптеры, установка описана ниже. На Docker-стенде кластера проверен fencing namespace; отдельно добавлены автоматические тесты адаптеров с имитацией провайдеров и локальным HTTPS. Реальные Proxmox, VMware, Hyper-V, libvirt и физические BMC этими тестами не проверяются: перед рабочим включением выполните приёмку в своей инфраструктуре.

## Готовые адаптеры: установка из исходников

В репозитории теперь есть исполняемые адаптеры:

- `scripts/godhcp-fence-peer` — Linux-диспетчер на Python 3: Proxmox (`qm`), KVM (`virsh`), IPMI (`ipmitool`), Redfish (HTTPS) и SSH-транспорт к ограниченному обработчику.
- `scripts/godhcp-fence-windows.ps1` и `scripts/GodhcpFencing.psm1` — обработчик для Hyper-V и VMware PowerCLI на Windows-шлюзе.
- [Пример конфигурации реплики](../deploy/fencing/node.example.json) и [параметры провайдеров](../deploy/fencing/providers.example.json).

Используется JSON, без дополнительных библиотек Python. Пакеты до 0.1.15 этих файлов не содержат. В пакетах 0.1.15 Linux-адаптеры установлены в `/usr/libexec/godhcp/`, Windows-файлы — в `/usr/share/godhcp/fencing/`, шаблоны — в `/usr/share/doc/godhcp/examples/`. Для пакетной установки используйте эти абсолютные пути в `fence`/`ip_up`/`ip_down`; ручная установка ниже использует `/usr/local/sbin`. Бинарные архивы содержат каталоги `scripts/` и `deploy/` для ручной установки. Это готовые программы; после установки нужно заполнить карту **ваших** объектов, настроить доступ и выполнить приёмку. Команды подготовки не выключают серверы, но вызов адаптера с node-id действительно выключает цель.

### На каждой Linux-реплике

Из корня репозитория:

```sh
sudo install -d -o root -g godhcp -m 0750 /etc/godhcp/fencing
sudo install -o root -g root -m 0755 scripts/godhcp-fence-peer /usr/local/sbin/godhcp-fence-peer
sudo install -o root -g godhcp -m 0640 deploy/fencing/node.example.json /etc/godhcp/fencing.json
```

Для Debian нужны Python 3 и `openssh-client`, для Rocky — Python 3 и `openssh-clients`. Для прямого IPMI дополнительно установите `ipmitool`. Redfish использует стандартную библиотеку Python и CA, указанный в конфигурации. Проверяйте пути: адаптер вызывает `/usr/bin/ssh`, `/usr/bin/ipmitool`, а обработчики гипервизоров — `/usr/sbin/qm`, `/usr/bin/pvesh`, `/usr/bin/virsh`.

В `fencing.json` задайте `local_node` равным `node` из `cluster.yml`. В `targets` поместите записи всех остальных реплик с их точными node-id. На каждой реплике получится своя карта. Не оставляйте демонстрационные имена `pve-example` и UUID из примера.

`restart_disabled: false` в шаблонах намеренно блокирует выполнение. После реального отключения независимого автоматического запуска поставьте `true`. Это подтверждение администратора, а не команда отключения HA: адаптер не может обнаружить все внешние планировщики, watchdog и политики питания. Proxmox дополнительно проверяет отсутствие ресурса в PVE HA, lock и `onboot`; KVM — autostart; Hyper-V — `IsClustered` и `AutomaticStartAction`.

В `/etc/godhcp/cluster.yml`:

```yaml
fence: [/usr/local/sbin/godhcp-fence-peer, --config, /etc/godhcp/fencing.json]
```

Файлы конфигурации должны быть обычными, принадлежать root либо эффективному пользователю процесса и не иметь записи для группы/остальных. В рабочей установке используйте root-owned файлы и каталоги. Пароли не должны быть доступны остальным пользователям. Проверка JSON отвергает повторяющиеся/неизвестные ключи выбранной цели и пустые поля.

### Proxmox и KVM: обработчик на фиксированном гипервизоре

Поддерживается фиксированный владелец VM без автоматической миграции/HA. Для Proxmox берите UUID из `qm config VMID` (`smbios1: uuid=...`); для KVM — `virsh domuuid NAME`. Адаптер сверяет UUID перед выключением. Для каждой VM оставьте в конфигурации её гипервизора только соответствующий node-id, например:

```json
{
  "local_node": "pve-b-management",
  "targets": {
    "b": {
      "provider": "proxmox", "restart_disabled": true,
      "vmid": 202, "uuid": "ЗАМЕНИТЕ-НА-UUID-VM"
    }
  }
}
```

Для KVM запись `b` имеет поля `provider: "kvm"`, `restart_disabled: true`, `uuid`; поля `vmid` быть не должно. `local_node` на гипервизоре — отдельное имя управляющего хоста, поскольку он выключает гостя, а не себя.

Установите Python-скрипт по тому же пути и конфигурацию `/etc/godhcp/fencing.json` на гипервизоре. Для `qm`/`pvesh` нужен привилегированный контекст; для libvirt — доступ к системному libvirt. Практический вариант — отдельный SSH-ключ с принудительной командой у root, **без произвольного shell**. Не разрешайте root-вход с паролем. Если политика запрещает root SSH, администратор гипервизора должен предоставить эквивалентный ограниченный исполнитель с нужными правами.

Строка для `authorized_keys` гипервизора (вместо последнего поля — публичный ключ реплики):

```text
restrict,command="/usr/local/sbin/godhcp-fence-peer --config /etc/godhcp/fencing.json --ssh-dispatch" ssh-ed25519 AAAA... godhcp-fence
```

По возможности добавьте `from="IP-РЕПЛИКИ"`; используйте разные ключи для разных инициаторов. `--ssh-dispatch` принимает только один node-id из `SSH_ORIGINAL_COMMAND`, не исполняет переданную командную строку. При необходимости ограничьте ключ отдельным конфигурационным файлом с единственной разрешённой целью.

На реплике запись `b` теперь указывает на гипервизор:

```json
{
  "provider": "ssh", "restart_disabled": true,
  "host": "pve-b.example.net", "user": "root",
  "key_file": "/etc/godhcp/fencing/id_ed25519",
  "known_hosts": "/etc/godhcp/fencing/known_hosts"
}
```

Закрытый ключ должен читаться службой (например `godhcp:godhcp`, 0600), родительский каталог — принадлежать root и быть недоступным службе для записи. В known_hosts заранее поместите проверенный ключ гипервизора. SSH должен работать без пароля/подтверждения и без agent forwarding. Используются строгая проверка ключа, фиксированный identity и `BatchMode=yes`; пользовательский `~/.ssh/config` не читается.

При миграции VM эта конфигурация перестаёт быть корректной. Автоматическую миграцию запретите, ручную проводите только в окне обслуживания с обновлением карты. Динамическое обнаружение владельца, PVE HA и oVirt/OpenStack этим адаптером не поддерживаются; ошибки блокируют переключение.

### VMware и Hyper-V: Windows-обработчик

На фиксированном Hyper-V-хосте установите PowerShell 7 и модуль Hyper-V. Для VMware подготовьте Windows-шлюз вне DHCP-VM, PowerShell 7 и поддерживаемый VMware PowerCLI (`VMware.VimAutomation.Core`). Установите доверенный CA vCenter в Windows. Доступ к vCenter проверяется с `InvalidCertificateAction Fail`.

Скопируйте `godhcp-fence-windows.ps1` и `GodhcpFencing.psm1` в `C:\ProgramData\GoDHCP`. Конфигурация `C:\ProgramData\GoDHCP\fencing.json` имеет ту же структуру `local_node`/`targets`. Для Hyper-V:

```json
{
  "local_node": "hyperv-b-management",
  "targets": {
    "b": {
      "provider": "hyperv", "restart_disabled": true,
      "uuid": "ЗАМЕНИТЕ-НА-GUID-VM"
    }
  }
}
```

GUID получите через `Get-VM | Select-Object Name,Id`. Обработчик работает с локальным Hyper-V, отвергает кластерные VM и включённый AutomaticStartAction. Запускается с правами управления этими VM. Поддержки Failover Cluster в этом адаптере нет.

Для VMware запись `b` замените на:

```json
{
  "provider": "vmware", "restart_disabled": true,
  "server": "vcenter.example.net", "vm_id": "VirtualMachine-vm-123",
  "uuid": "ЗАМЕНИТЕ-НА-SMBIOS-UUID-VM",
  "credential_file": "C:\\ProgramData\\GoDHCP\\vcenter.credential.xml"
}
```

После подключения PowerCLI получите `Id` и `ExtensionData.Config.Uuid` нужной VM; UUID BIOS и InstanceUuid — разные поля, здесь нужен первый. Отключите HA restart/VM Monitoring/autostart именно для этих VM по инструкции ниже. При недоступном ESXi-владельце обработчик отвергает кэшированный PowerState, даже если vCenter доступен. Перед остановкой и при подтверждении заново проверяются UUID и ConnectionState хоста.

Создайте credential-файл **под той Windows-учётной записью и на том шлюзе**, от которых будет выполняться SSH-обработчик:

```powershell
Get-Credential | Export-Clixml -LiteralPath C:\ProgramData\GoDHCP\vcenter.credential.xml
```

Используется Windows DPAPI. Не копируйте файл на другую машину/под другого пользователя и не создавайте его на Linux, где Export-Clixml не обеспечивает такую защиту. У роли vCenter нужны чтение VM/ESXi и Power Off только целевых VM.

В OpenSSH Server создайте отдельную учётную запись, настройте вход только по ключам. В её `Match User` задайте фиксированный обработчик (путь к PowerShell проверьте на своём сервере):

```text
Match User godhcp-fence
    AuthenticationMethods publickey
    AllowTcpForwarding no
    PermitTTY no
    ForceCommand "C:/Program Files/PowerShell/7/pwsh.exe" -NoLogo -NoProfile -NonInteractive -File C:/ProgramData/GoDHCP/godhcp-fence-windows.ps1
```

Проверьте конфигурацию `sshd -t` перед перезапуском SSH. Настройте approved `authorized_keys` с учётом правил Windows OpenSSH для административных пользователей. ACL на каталог, скрипты, JSON и credential-файл: запись только Administrators/SYSTEM, сервисной учётной записи — чтение/выполнение; credential не должен читаться посторонними. Не давайте этому ключу отдельный неограниченный путь входа.

На Linux-репликах используйте `provider: "ssh"`, адрес Windows-хоста, пользователя `godhcp-fence`, ключ и known_hosts. Параметры `provider: "vmware"` и `"hyperv"` находятся **только в Windows-конфигурации**, не в Linux-диспетчере. Успех передаётся строкой `FENCED <node-id>` и кодом 0; лишний вывод либо отсутствие строки отклоняются.

Windows-обработчик запускает работу в отдельном job с ожиданием до 17 секунд. Вход в PowerCLI/импорт модуля также расходуют бюджет. Если первый запуск платформы слишком медленный, переключение будет заблокировано; предварительно измерьте время. Увеличение внешнего таймаута GoDHCP не реализовано этим изменением.

### IPMI и Redfish напрямую с реплики

Для IPMI используйте поля из `ipmi-example` в [шаблоне провайдеров](../deploy/fencing/providers.example.json), переименовав ключ в node-id. Получите `guid` через `ipmitool ... mc guid`. Перед power off адаптер сверяет именно этот GUID; нулевой GUID не принимается. Пароль хранится в файле, передаётся `ipmitool -f`, не в аргументах пароля и не через журнал. Повторный вызов при Off не выполняет power off снова.

Для Redfish используйте запись из [примера реплики](../deploy/fencing/node.example.json). После безопасной инвентаризации заполните `system_uri`, UUID и SerialNumber реального ComputerSystem, путь к доверенному CA и файлу пароля. Здесь URI указан явно: адаптер не выбирает автоматически первую систему из шасси.

Redfish использует Basic Auth **только поверх проверенного HTTPS**, без создания постоянной сессии. HTTP proxy из окружения и перенаправления отключены. Target действия и ActionInfo разрешены только внутри `/redfish/v1/` того же BMC. Требуется явное объявление поддержки ForceOff через AllowableValues или ActionInfo. При отсутствии метаданных операция отклоняется: совместимость с конкретной прошивкой проверяйте отдельно. После POST выполняется опрос ComputerSystem до фактического Off; ответ 202 сам по себе не даёт успеха. Пароль и ответы сервера не выводятся при ошибках.

### Проверки адаптеров

Из корня репозитория:

```sh
make test-fencing
make test-fencing-windows
```

Первая команда запускает Python unittest, включая настоящий локальный HTTPS-сервер с одноразовым сертификатом (нужен `openssl`). Вторая использует локальный `pwsh`, а при его отсутствии — контейнер `mcr.microsoft.com/powershell:7.4-debian-12`; контейнер тестов запускается без сети. Для первоначальной загрузки образа нужен доступ к registry. В тестах команды управления VM/BMC подменены, рабочие машины не выключаются.

Проверяются выключение и повторный вызов, UUID/GUID, запрещённый autostart/HA, недоступный ESXi, отказ команды, таймаут, SSH-подтверждение, сертификат/имя сервера, перенаправления и отсутствие утечки секрета в диагностике. Это не заменяет аппаратную приёмку ниже. 19 ноября 2026 года прошли 23 Python-теста и 17 сценариев PowerShell (12 провайдерных и 5 через диспетчер), плюс проверка синтаксиса. PowerShell запускался в Linux-контейнере с подменой команд провайдеров; реальные Windows OpenSSH, DPAPI, Hyper-V и PowerCLI требуют проверки на целевом шлюзе.

Для реальной проверки в окне обслуживания выполните на реплике от пользователя службы:

```sh
sudo -u godhcp /usr/local/sbin/godhcp-fence-peer --config /etc/godhcp/fencing.json b
```

**Команда действительно выключает b.** Ожидаются `FENCED b`, код 0 и подтверждённый Off на контроллере. Затем выполните проверку через сам кластер под systemd: ручной `sudo -u` не воспроизводит все ограничения unit. При ошибке адаптер возвращает ненулевой код без содержимого секретов; причину ищите в состоянии объекта и журнале управляющей платформы. Не запускайте параллельно ручные и автоматические операции возврата питания.

## 1. Общие требования

Разместите три реплики в разных доменах отказа. Если все они работают на одном гипервизоре, выключение этого хоста лишит кластер кворума. Управление гипервизорами/BMC должно идти по отдельной управляющей сети, доступной оставшимся репликам. Шлюз управления нельзя размещать на выключаемом узле.

Для каждого node-id заведите фиксированное соответствие инфраструктурному объекту:

- `a` → конкретный VMID/UUID виртуальной машины либо адрес BMC и серийный номер сервера;
- `b` и `c` → собственные объекты;
- неизвестный node-id, собственный node-id, неоднозначный объект → ошибка без выключения.

Не ищите цель только по отображаемому имени и не принимайте адрес BMC/произвольную команду из аргумента hook. Пересоздание VM, миграция или замена системной платы требует проверки соответствия. Для BMC проверьте серийный номер в инвентаризации до разрешения управления питанием.

Операция должна быть **off**, а не reboot/reset/cycle: перезапущенный узел может снова обслуживать сеть. Перед вводом исключите независимый автоматический запуск VM/хоста средствами HA, watchdog, планировщиков, UPS и политик восстановления питания. Не отключайте HA всего гипервизорного кластера: настройка относится к конкретным DHCP-репликам.

Выключение должно охватывать весь узел, включая дочерние DDNS-команды. Отключение только DHCP-порта, снятие VIP или отсутствие ping не является достаточным fencing. При сетевом варианте пришлось бы гарантированно перекрыть все пути DHCPv4/v6, API, DNS-обновлений и обходные интерфейсы; данный документ рекомендует выключение питания.

## 2. Подключение к GoDHCP

На каждой реплике в `/etc/godhcp/cluster.yml`:

```yaml
fence: [/usr/local/sbin/godhcp-fence-peer]
```

Координатор вызовет, например, `/usr/local/sbin/godhcp-fence-peer b`. Команда запускается напрямую, без shell; node-id добавляется последним аргументом. Дополнительные фиксированные аргументы можно указать элементами YAML-массива. Параметров `fencing_timeout` или `provider` в манифесте нет.

Контракт адаптера:

1. Проверить число аргументов, node-id и фиксированную карту целей.
2. Подключиться к авторитетному контроллеру с проверкой TLS/SSH-ключа. Проверить личность объекта и актуальность состояния.
3. Если объект уже достоверно выключен и автоматический запуск исключён — вернуть 0.
4. Иначе выполнить принудительное выключение, дождаться завершения операции и повторно запросить состояние.
5. Вернуть 0 только при подтверждённом `Off`/`PoweredOff`/`shut off`/`stopped`. Ошибка связи, отказ доступа, отсутствующий объект, переходное состояние или таймаут означают ненулевой код.

HTTP 200/202, идентификатор фоновой задачи и успешная отправка команды не подтверждают выключение. Кэшированное состояние отключённого от управления гипервизора также не подходит.

**Текущие ограничения:** один hook ограничен 20 секундами; вся попытка активации — 90 секундами. Эти значения заданы в коде. Закладывайте в 20 секунд соединение, авторизацию, выключение и проверку; собственный бюджет адаптера делайте меньше, например 18 секунд. Ограничивайте также каждый сетевой запрос. Если платформа не укладывается, активация должна завершиться ошибкой: не возвращайте успех заранее. Внешняя операция может закончиться после таймаута; следующий вызов обязан безопасно распознать уже выключенную цель. Изменение таймаута требует отдельной доработки и проверки GoDHCP.

Скрипты и карта целей должны принадлежать root и быть недоступны службе для записи. Секреты храните отдельно, например `root:godhcp`, режим 0640, каталог 0750. Не помещайте пароли в аргументы процессов, YAML-манифест, Git или логи. Учётной записи выдавайте только чтение состояния и выключение разрешённых целей, если платформа поддерживает такую детализацию.

Unit GoDHCP работает от `godhcp` с `NoNewPrivileges=true`: локальный `sudo` внутри hook не следует считать работающим способом повышения прав. Используйте API/BMC либо отдельный шлюз с ограниченным обработчиком. Сохраните `KillMode=control-group`. Проверяйте интеграцию в реальных ограничениях unit, а не только из root-shell.

### Шлюз управления по SSH

На Linux-шлюзе можно установить root-owned обработчик, который принимает только `a`, `b`, `c`, выбирает фиксированную цель и вызывает инструмент провайдера. На SSH-ключе ограничьте команду через `authorized_keys` (`restrict,command="/usr/local/sbin/godhcp-fence-dispatch"`), запретите shell, forwarding и произвольные аргументы. Обработчик должен строго разобрать `SSH_ORIGINAL_COMMAND`, без `eval`.

Пример транспортного вызова из адаптера; `$target` уже проверен по карте целей:

```sh
ssh -F /dev/null -i /etc/godhcp/fencing/id_ed25519 \
  -o IdentitiesOnly=yes -o BatchMode=yes -o ConnectTimeout=3 \
  -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile=/etc/godhcp/fencing/known_hosts \
  fence@mgmt.example.net "$target"
```

Проверьте fingerprint шлюза заранее. Весь удалённый обработчик также должен иметь собственный таймаут. Обрыв SSH не гарантирует остановку удалённой команды, поэтому она должна только выключать фиксированную цель и быть безопасной при повторе. Шлюз — часть инфраструктуры доступности; при его отказе переключение блокируется.

## 3. Proxmox VE

Для простейшей схемы закрепите каждую VM за отдельным PVE-хостом, исключите миграцию и удалите именно эти VM из управления PVE HA. Делайте это в согласованное окно обслуживания: изменение HA-состояния может остановить VM. Не используйте состояние HA `disabled` как постоянный режим работающей VM — менеджер держит такой ресурс выключенным. Управление возвратом реплики выполняйте вручную.

В интерфейсе Datacenter → HA убедитесь, что DHCP-VM больше не управляется HA. В VM → Options отключите Start at boot. Эквивалент последней настройки на владельце VM:

```sh
qm set 201 --onboot 0
```

На шлюзе сопоставьте `a → pve-a/201`, `b → pve-b/202`, `c → pve-c/203`. Проверьте владельца и отсутствие миграции перед разрешением fencing. Для фиксированной VM на её PVE-хосте операции выглядят так:

```sh
qm status 201
qm stop 201 --timeout 10
qm status 201
```

Адаптер пропускает `stop`, если свежий статус уже `stopped`, иначе проверяет его после остановки. Ошибка команды или блокировка VM не должна обходиться через `--skiplock`. Вызовы `qm` требуют прав на PVE-хосте: выдавайте их только ограниченному серверному обработчику, не произвольному SSH-shell службы.

При интеграции через PVE API создайте отдельного пользователя/токен; ограничьте ACL путями нужных `/vms/<vmid>`, разрешив `VM.Audit` и `VM.PowerMgmt`, и выдайте минимальные дополнительные права, необходимые для чтения владельца/задачи. Используйте проверяемый HTTPS и секретный файл для токена. Запрос stop возвращает задачу: дождитесь её завершения и свежего `status/current = stopped`.

Если нужны миграция и PVE HA, адаптер должен находить актуального владельца через кластерный API, переводить ресурс в устойчивое выключенное желаемое состояние и проверять фактическое выключение на владельце. При недоступном владельце записи HA недостаточно: требуется fencing физического PVE-хоста, с учётом всех размещённых на нём VM и сохранения кворума. Простой фиксированный SSH-вариант для этой схемы непригоден.

Источники: [qm](https://pve.proxmox.com/pve-docs/qm.1.html), [PVE HA и состояния ресурсов](https://github.com/proxmox/pve-docs/blob/master/ha-manager.adoc), [API Viewer](https://pve.proxmox.com/pve-docs/api-viewer/).

## 4. VMware ESXi / vCenter

Создайте отдельную роль с чтением состояния и `Virtual machine → Interaction → Power off`, назначенную только DHCP-VM. Сопоставьте node-id с конкретным объектом внутри конкретного vCenter и дополнительно проверяйте UUID; отображаемое имя не уникально. Отключите для этих VM автоматический restart средствами vSphere HA, VM Monitoring и автозапуск ESXi. Уберите сторонние задания восстановления питания. Настройки зависят от версии vSphere и должны быть проверены тестом.

На управляющей машине установите PowerCLI, доверенный CA vCenter и настройте получение учётных данных из защищённого хранилища без интерактивного запроса. Не используйте `InvalidCertificateAction Ignore`. После аутентифицированного подключения к нужному vCenter логика выключения конкретной VM:

```powershell
# $vmId берётся из защищённой карты, например VirtualMachine-vm-123.
# До этого проверены vCenter, UUID и доступность ESXi-владельца.
$ErrorActionPreference = 'Stop'
$vm = Get-VM -Id $vmId -ErrorAction Stop
if ($vm.PowerState -ne 'PoweredOff') {
    Stop-VM -VM $vm -Confirm:$false -ErrorAction Stop | Out-Null
}
$vm = Get-VM -Id $vmId -ErrorAction Stop
if ($vm.PowerState -ne 'PoweredOff') { throw 'VM power-off not confirmed' }
```

Это фрагмент обработчика: он требует общей проверки цели, таймаута и запрета автоматического запуска. `Stop-VM` выполняет выключение VM; guest shutdown через VMware Tools для fencing не подходит. При отключённом ESXi vCenter может показывать устаревшее состояние. В такой ситуации не подтверждайте fencing по инвентарю: используйте независимый BMC ESXi либо завершайте попытку ошибкой. MoRef может измениться после перерегистрации VM — обновите карту после проверки UUID.

Источники: [PowerCLI Stop-VM](https://developer.broadcom.com/powercli/latest/vmware.vimautomation.core/commands/stop-vm), [PowerState](https://developer.broadcom.com/powercli/latest/vmware.vimautomation.core/structures/vmware.vimautomation.vicore.types.v1.inventory.powerstate).

## 5. Microsoft Hyper-V

Используйте Windows-шлюз с модулем Hyper-V и ограниченной административной точкой входа, например JEA/WinRM HTTPS или выделенным OpenSSH-обработчиком. Linux-служба GoDHCP вызывает шлюз; сам по себе `Stop-VM` в Linux-shell недоступен. Учётные данные Windows не передавайте в аргументах. Ограничьте серверную функцию фиксированными GUID виртуальных машин.

Для простого варианта используйте VM на фиксированных Hyper-V-хостах без управления Failover Cluster. Отключите автозапуск каждой DHCP-VM при старте гипервизора:

```powershell
Get-VM -Id $vmId -ErrorAction Stop | Set-VM -AutomaticStartAction Nothing
```

Фрагмент обработчика на правильном Hyper-V-хосте, где `$vmId` — проверенный GUID:

```powershell
$ErrorActionPreference = 'Stop'
$vm = Get-VM -Id $vmId -ErrorAction Stop
if ($vm.State -ne 'Off') {
    Stop-VM -VM $vm -TurnOff -Confirm:$false -ErrorAction Stop
}
$vm = Get-VM -Id $vmId -ErrorAction Stop
if ($vm.State -ne 'Off') { throw 'VM power-off not confirmed' }
```

`-TurnOff` выключает питание VM. Состояния Saved, Paused, Stopping и отсутствие ответа не подтверждают fencing. При использовании Failover Cluster необходимо дополнительно исключить автоматический restart/перенос роли, определить текущего владельца и проверить реальное `Off` на нём. Одного `AutomaticStartAction Nothing` для кластерной роли недостаточно. При потере владельца нужен BMC-fencing хоста либо отказ от переключения.

Источники: [Stop-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/stop-vm), [Set-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/set-vm).

## 6. KVM / libvirt и платформы на их основе

На каждом фиксированном гипервизоре сопоставьте node-id с UUID домена. Для DHCP-VM отключите libvirt autostart; в управляющей платформе также исключите автоматическое восстановление/миграцию. Выдайте шлюзу доступ только к разрешённым доменам и операциям; членство в общей группе libvirt часто даёт существенно больше прав.

```sh
virsh -c qemu:///system autostart "$uuid" --disable
```

Операции обработчика на гипервизоре:

```sh
LC_ALL=C virsh -c qemu:///system domstate "$uuid"
virsh -c qemu:///system destroy "$uuid"
LC_ALL=C virsh -c qemu:///system domstate "$uuid"
```

Перед `destroy` проверьте состояние: уже выключенный домен не нужно выключать повторно. Успех — только свежий `shut off`. `destroy` принудительно останавливает VM, но не удаляет её определение и диски; **не используйте `undefine`**. Не принимайте paused или pmsuspended за выключение.

Для oVirt, OpenStack и отечественных платформ виртуализации на KVM управление жизненным циклом может выполнять вышестоящий контроллер. Прямой `virsh destroy` без согласования с ним способен вызвать автоматический перезапуск VM. Используйте документированный API именно вашей платформы с устойчивым желаемым состоянием «выключено», запретом автоматического восстановления и проверкой фактического состояния. Наличие KVM внутри продукта не означает совместимость простого адаптера libvirt.

Источник: [официальное руководство virsh](https://www.libvirt.org/manpages/virsh.html).

## 7. Физические серверы: IPMI

Подходит для серверов с поддерживаемым IPMI BMC, в том числе соответствующих моделей Dell iDRAC, HPE iLO, Lenovo XCC и Supermicro. Возможности зависят от модели, лицензии и прошивки. Включите IPMI over LAN в управляющей сети, заведите отдельную учётную запись с разрешением чтения состояния и управления питанием. Установите `ipmitool` на реплики или шлюз. Не открывайте BMC в клиентскую сеть.

В BIOS/BMC задайте восстановление после потери питания в состояние Off/Stay Off. Исключите Wake-on-LAN, RTC wake, watchdog power-cycle и управляющие задания, способные включить fenced-хост. Убедитесь, что команда управляет именно сервером, а не всем шасси с другими репликами.

Пароль положите в отдельный защищённый файл. Операции для заранее проверенной цели:

```sh
ipmitool -I lanplus -H bmc-b.example.net -U godhcp-fence \
  -f /etc/godhcp/fencing/bmc-b.password chassis power status
ipmitool -I lanplus -H bmc-b.example.net -U godhcp-fence \
  -f /etc/godhcp/fencing/bmc-b.password chassis power off
ipmitool -I lanplus -H bmc-b.example.net -U godhcp-fence \
  -f /etc/godhcp/fencing/bmc-b.password chassis power status
```

Адаптер проверяет коды возврата, пропускает off для уже выключенной цели и опрашивает статус до `Chassis Power is off` в пределах общего бюджета. Ответ команды power off сам по себе недостаточен. IPMI использует собственный протокол, не TLS: mTLS GoDHCP не защищает связь с BMC. Используйте `lanplus` с настройками аутентификации/шифрования, поддерживаемыми и проверенными на BMC, и изолированную управляющую сеть. Если политика требует HTTPS, рассмотрите Redfish.

Источник: [руководство ipmitool](https://github.com/ipmitool/ipmitool/blob/master/doc/ipmitool.1.in).

## 8. Физические серверы: Redfish по HTTPS

Предпочтителен при наличии поддерживаемой реализации Redfish и доверенного сертификата BMC. Для iDRAC/iLO/XCC и других BMC проверьте документацию конкретной прошивки. Не отключайте проверку TLS (`curl -k` недопустим). Синхронизируйте время, установите CA и используйте имя из SAN сертификата.

Настройка адаптера:

1. Создать отдельную учётную запись BMC с чтением ComputerSystem и управлением питанием. Сохранить секрет в защищённом хранилище; использовать Redfish Session или защищённый конфигурационный файл клиента, не пароль в командной строке.
2. Прочитать `/redfish/v1/Systems`, выбрать член коллекции по проверенным UUID/SerialNumber и зафиксировать его URI в карте целей. Не предполагать, что идентификатор всегда `1` или `System.Embedded.1`.
3. Прочитать ресурс ComputerSystem. В `Actions["#ComputerSystem.Reset"].target` получить адрес действия; проверить поддержку `ForceOff` через AllowableValues/ActionInfo и документацию прошивки. Разрешать запросы только к ожидаемому BMC, не перенаправлять токен на произвольный URL.
4. Если `PowerState` уже `Off`, подтвердить это свежим чтением. Иначе выполнить POST на обнаруженный target с JSON `{"ResetType":"ForceOff"}`.
5. При асинхронном ответе отслеживать задачу, затем повторно читать ComputerSystem до `PowerState == "Off"`. Ошибка задачи, таймаут или другое состояние — ненулевой exit code.
6. Завершить сессию при возможности; токены и пароли не записывать в журнал. Не позволять очистке сессии скрыть ошибку выключения.

`GracefulShutdown` может зависнуть вместе с ОС; `ForceRestart` снова включает сервер. Для этой схемы нужен именно `ForceOff`. Учётные данные и CA настраиваются отдельно от peer mTLS кластера. Политику восстановления питания и запрет независимого запуска настройте так же, как для IPMI.

Источники: [DMTF Redfish ComputerSystem и Reset](https://redfish.dmtf.org/schemas/v1/DSP2046_2024.1.html), [спецификация модели Redfish](https://redfish.dmtf.org/schemas/v1/DSP0268_2025.3.html).

## 9. Сервер без BMC: управляемый PDU

Допустим PDU с независимым управлением розетками и проверкой их фактического состояния. Зафиксируйте node-id → PDU/розетки. Для сервера с двумя блоками питания отключайте **обе** линии; подтверждение одной розетки недостаточно. Розетки не должны питать другие реплики, сетевое оборудование или сам управляющий шлюз.

Используйте документированный API производителя с проверкой TLS либо SNMPv3 authPriv, команду Off без автоматического On и чтение фактического состояния всех назначенных выходов. Возможность «выключить на несколько секунд» для fencing не подходит. Если достоверно подтвердить отсутствие питания нельзя, адаптер возвращает ошибку. Возврат питания — отдельная ручная процедура.

## 10. Приёмка и возврат узла

Проверки с выключением выполняйте на выделенных тестовых VM/серверах или в согласованное окно. Сначала сверяйте node-id и инвентаризацию, затем разрешайте питание. Рекомендуемый порядок:

1. Проверить доступ к управлению из каждой реплики с правами и ограничениями systemd-службы. Убедиться, что секреты не попадают в журнал, TLS/SSH-проверка включена.
2. Выключить выбранную тестовую цель через hook: код 0 появляется только после подтверждения Off. Повторный вызов для уже выключенной цели тоже успешен. Неизвестная и собственная цель отклоняются.
3. Проверить неверные credentials, недоступный контроллер, TLS-ошибку, зависшую задачу и превышение 20 секунд. Каждый случай блокирует активацию, новый VIP не появляется.
4. Оставить клиентскую сеть старого лидера доступной, разорвать только peer TCP. Убедиться, что перед переносом IPv4/IPv6 VIP прежняя VM/машина действительно выключена; DHCP/DDNS с неё отсутствуют.
5. Проверить получение и продление DHCPv4/v6 напрямую и через relay, сохранение адресов и DUID, обновление Samba DNS. Зафиксировать время fencing и всего переключения.
6. Проверить отсутствие самопроизвольного включения при работе HA/watchdog и после восстановления управления/питания. Проверить потерю кворума: выдача и VIP должны прекращаться.
7. Сохранить журналы GoDHCP, задачи гипервизора/BMC и сетевой захват с временем. Один только статус службы `active` не является результатом приёмки.

Для возврата устраните причину отказа, проверьте отсутствие статического VIP в сетевой конфигурации и сохранность исходного каталога Raft. Снимите инфраструктурную блокировку и вручную включите **один** узел. Он должен присоединиться с прежней identity и журналом, не выдавая DHCP параллельно действующему владельцу VIP. Не удаляйте Raft-каталог и не включайте bootstrap повторно. Независимое автоматическое восстановление питания оставьте отключённым, если адаптер не обеспечивает согласованное управление им.

Если выключение не подтвердилось, сохраняйте неактивное состояние нового узла и исправляйте доступ/адаптер. Нельзя обходить ошибку скриптом `exit 0`, принудительным назначением VIP или запуском standalone-демона на том же пуле.
