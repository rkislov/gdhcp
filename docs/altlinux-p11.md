## Архитектуры и границы поддержки

Поставляются отдельные RPM с архитектурой в имени и заголовке пакета:

- `x86_64` — Intel/AMD 64-bit, Go `amd64`.
- `aarch64` — ARMv8 64-bit, Go `arm64`.
- `i586` — x86 32-bit, Go `386`, `GO386=softfloat` (без требования SSE2).
- `loongarch64` — LoongArch64, Go `loong64`; дополнительная сборка для проверки на целевой платформе.
- `riscv64` — RISC-V 64-bit, Go `riscv64`; дополнительная сборка для проверки на целевой платформе.

В открытом [репозитории p11](https://download.basealt.ru/pub/distributions/ALTLinux/p11/branch/) доступны x86_64, aarch64 и i586. Для armh/ARMv7 и ppc64le ветка p11 не создавалась, см. [анонс ALT](https://lists.altlinux.org/pipermail/altlinux-announce-en/2024/000039.html). Эти архитектуры не следует подменять пакетами с маркировкой p11.

На [странице платформы BaseALT](https://www.basealt.ru/platform) LoongArch указан в числе поддерживаемых платформ, а RISC-V — среди подготавливаемых репозиториев. [Образ ALT Server для LoongArch64](https://www.basealt.ru/alt-server/download) предлагается как technical preview по запросу. Наличие RPM для этих двух архитектур означает успешную кросс-сборку и проверку содержимого, **не подтверждённую совместимость с закрытым/предварительным образом ALT**. До рабочего использования нужна установка и приёмка на целевом сервере.

Эльбрус e2k исключён из поставки по согласованному объёму. Стандартный Go не предоставляет цель e2k; смена метки RPM не создаёт совместимый бинарник.

## Как выбрать пакет

Проверьте архитектуру ОС и пакетного менеджера:

```sh
uname -m
rpm --eval '%{_arch}'
```

Для 32-битной ALT выбирайте i586, даже если процессор способен работать в 64-битном режиме. Соответствие файла:

```text
godhcp-0.1.20-alt1.p11.x86_64.rpm
godhcp-0.1.20-alt1.p11.aarch64.rpm
godhcp-0.1.20-alt1.p11.i586.rpm
godhcp-0.1.20-alt1.p11.loongarch64.rpm
godhcp-0.1.20-alt1.p11.riscv64.rpm
```

Для обычного сервера Intel/AMD скачайте первый файл. Пакет ALT p10 имеет отдельный суффикс `alt1.p10`; не используйте его вместо p11. `x86_64-i586` в репозитории ALT — multilib, отдельный бинарник GoDHCP для него не требуется.

## Установка и проверка целостности

Скачайте пакет и `SHA256SUMS` из одного релиза. Пример для x86_64:

```sh
grep '  godhcp-0.1.20-alt1.p11.x86_64.rpm$' SHA256SUMS | sha256sum -c -
sudo apt-get install ./godhcp-0.1.20-alt1.p11.x86_64.rpm
/usr/bin/godhcp version
rpm -V godhcp
```

Для другой архитектуры замените суффикс файла в обеих командах. Продолжайте только после результата контрольной суммы OK. Пакеты не подписаны; SHA-256 проверяет целостность файла, а не доверие к издателю.

Установщик создаёт системную учётную запись godhcp и каталоги, но **не включает DHCP автоматически**. Зависимости: systemd, shadow-utils, util-linux, logrotate и Python 3. Бинарник статический, веб-интерфейс встроен; Node.js не нужен. Не используйте `rpm --nodeps` или `--ignorearch` для обхода ошибок установки на рабочем сервере.

## Обычный сервер

Исходный пример находится в `/etc/godhcp/config.yml.example`. Подготовьте `/etc/godhcp/config.yml` и `/etc/godhcp/godhcp.env` по основному PDF-руководству. В примере DHCP отключён (`server.listen: "-"`); для выдачи IPv4 требуется `":67"`. Убедитесь, что порт свободен, и согласуйте переключение с прежнего DHCP.

```sh
/usr/bin/godhcp -validate -config /etc/godhcp/config.yml
sudo systemctl enable --now godhcp
sudo systemctl status godhcp
sudo journalctl -u godhcp -f
```

При ручной валидации передайте переменные окружения, которые использует конфигурация. Файл godhcp.env автоматически читает systemd, а не произвольная shell-команда. API в пакетном примере доступен на `127.0.0.1:8181`; доступ извне и авторизацию настройте до открытия порта.

## Автоматический кластер и fencing

Трёхузловой кластер Raft остаётся экспериментальным: три Linux-реплики, mTLS, один активный DHCP/API/DDNS. Отдельный двухузловой active-backup описан в CLUSTER-OPERATIONS.md. Установка RPM сама по себе его не включает.

Файлы пакета:

- `/usr/libexec/godhcp/godhcp-fence-peer` — Linux fencing.
- `/usr/libexec/godhcp/godhcp-cluster-ip` — перенос VIP.
- `/usr/share/godhcp/fencing/` — Windows-обработчики VMware/Hyper-V.
- `/usr/share/doc/godhcp/examples/cluster/` — манифест и systemd drop-in.
- `/usr/share/doc/godhcp/examples/fencing/` — JSON-шаблоны целей.

Установите дополнительные инструменты выбранного механизма: iproute2/iproute и arping для VIP, OpenSSH client для SSH либо ipmitool для IPMI. Проверьте реальные имена пакетов и пути команд в своей редакции ALT. Redfish работает через Python с проверенным HTTPS и отдельным CA.

Настройте три постоянных peer-адреса, сертификаты, фиксированную карту fencing и выделенный service IP. Используйте [руководство кластера](cluster-runtime.md) и [инструкцию fencing](fencing.md), включённые в основной PDF. Пример ссылки на установленный hook:

```yaml
fence: [/usr/libexec/godhcp/godhcp-fence-peer, --config, /etc/godhcp/fencing.json]
```

`restart_disabled: true` разрешено ставить только после фактического отключения независимого автоматического запуска VM/хоста. Потеря ping не является подтверждением выключения.

**Автоматического переноса существующих аренд в Raft нет. Не включайте пустой кластер на действующем пуле.** Подготовьте отдельный пул либо проверенный план переноса/карантина. Для каждой архитектуры отдельно проведите сетевую приёмку и проверку fencing; успешная установка пакета её не заменяет.

## Проверки сборок

Скрипт `scripts/test-altlinux-p11.sh` проверяет x86_64, aarch64 и i586 в соответствующих официальных контейнерах ALT p11: установку с зависимостями, реальную версию бинарника, наличие PDF/адаптеров, unit-файл, повторную установку, удаление и сохранение конфигурации/данных. Для i586 в среде, где нет прямого выполнения x86-32, допускается запуск через qemu-i386; это отдельно отмечается в отчёте.

LoongArch64 и RISC-V проходят проверку ELF-архитектуры, метаданных RPM и совпадения извлечённого бинарника с результатом сборки. Дополнительно `scripts/test-altlinux-p11-ports.sh` запускает бинарник и тесты кластера под QEMU: mTLS, сохранение состояния и переключение Raft. Это эмуляция CPU в Linux-контейнере, а не испытание ALT на целевом оборудовании. Нативная установка, загрузка systemd и выдача DHCP на этих двух платформах не проверены. Не считайте отсутствие аппаратного стенда успешным испытанием.

## Воспроизводимость

```sh
bash scripts/build-altlinux-p11.sh
bash scripts/test-altlinux-p11.sh
bash scripts/test-altlinux-p11-ports.sh
```

По умолчанию собираются пять перечисленных архитектур. Для подмножества:

```sh
GODHCP_ALT_P11_ARCHES='x86_64 aarch64 i586' bash scripts/build-altlinux-p11.sh
```

Требуются Go, Docker, Python 3 и ripgrep. Упаковка выполняется настоящим rpm-build из ALT p11. Исходники бинарника берутся из чистого клона тега `v0.1.20` (`PACKAGE_TAG` позволяет выбрать другой тег). Версия пакета должна совпадать с версией этого тега. Основная VCS-ревизия бинарника указывает на этот тег. Для LoongArch64/RISC-V создаются изолированные копии BoltDB v1.3.1 и bbolt v1.3.5 с недостающими архитектурными константами; для старого BoltDB включён консервативный режим выравнивания. База данных и её формат не меняются. Состав дополнений и их SHA-256 записаны в `PORTABILITY.json`, полные копии модулей с дополнениями поставляются отдельным архивом. Исходники кэша Go не меняются. Инструкции и рецепт дополнительной упаковки p11 имеют отдельную ревизию `PACKAGING_COMMIT`. Опубликованный тег основного релиза не перемещается.

Результат: `dist/altlinux-p11/0.1.20/`, включая RPM, отдельные бинарники, BUILDINFO для каждой архитектуры и SHA256SUMS. Дополнительный архив исходников упаковки ALT p11 содержит рецепт и инструкции. Для запуска скрипта клонируйте Git-репозиторий и переключитесь на коммит `PACKAGING_COMMIT`; тег основной программы также должен присутствовать в клоне.

Пара active/backup и трёхузловой Raft настраиваются по [пошаговой инструкции](cluster-operations.md). Обновление пакета не включает кластер автоматически.
