## PCP

До исправления PCAP показывал PCP=0 при настройке `priority: 6`. UDP-транспорт не применял рассчитанный ядром приоритет. Теперь на Linux используется SO_PRIORITY; для локального NAK приоритет берётся из входного VLAN, даже если запрошенный IP не подходит подсети.

На интерфейсах стенда заданы identity egress-qos-map 0:0 … 7:7. Захват исходящих OFFER/ACK/NAK подтвердил VLAN 20/PCP 6 и VLAN 30/PCP 5. Уровень ядра проверяется отдельным Linux-тестом: установка SO_PRIORITY 6, затем 5 и сброс в 0. Проверка захвата исключает ICMP с вложенным DHCP-пакетом: вложенная копия не является ответом сервера.

Повторный запуск: `make test-dhcp-docker`. Всего прошла 21 проверка: 20 в основном контейнере и одна после его пересоздания. PCAP и JSON сохраняются в `output/dhcp-lab/`; захват этого прогона также сохранён в `output/pcp/`. Настройка ОС и права описаны в [vlans.md](vlans.md#pcp-на-linux).

## Методика нагрузки

```bash
make test-load-docker
# Более продолжительный прогон:
bash scripts/test-load-docker.sh --seconds 60
```

Docker Desktop, Linux 7.0.14-linuxkit, ARM64. Лимит контейнера — 4 vCPU и 2 GiB RAM; сервер и генератор делят этот лимит. Сервер GOMAXPROCS=4, генератор GOMAXPROCS=1. Это виртуальный стенд veth/network namespace, не физический Raspberry Pi. Внешние сети и интерфейсы хоста не используются (`--network none`).

В SQLite заранее записаны 100 000 активных аренд, загруженных сервером при старте. Перед каждым сценарием восстанавливается одинаковая БД и запускается новый процесс. SQLite WAL, synchronous=NORMAL, ping-check выключен, журнал уровня error. Каждый сценарий отправляет пакеты 10 секунд; после отправки ответы собираются ещё не более 5 секунд. Увеличение срока аренды выполняется настоящим DHCPREQUEST/ACK с записью в SQLite; INFORM проверяет обработку пакетов без сохранения аренды. Это не измерение полной транзакции DORA.

Go-генератор выполняет открытый цикл с заданной частотой; ожидание ответа не замедляет подачу следующих запросов. Для relay он имитирует агент, отправляя пакеты с giaddr, hops и опцией 82 напрямую серверу на UDP 67. Это измеряет обработку relay сервером, а не производительность отдельного процесса ISC dhcrelay. Проверяются тип ответа, XID, MAC, выданный IP и точное эхо опции 82. Неправильные и повторные ответы считаются отдельно.

Задержка измеряется от планового времени отправки до получения корректного ответа, включая отставание генератора от графика. Перцентили относятся только к полученным ответам: при потерях их нельзя трактовать как задержку всех запросов. `unanswered` означает отсутствие корректного ответа к завершению окна сбора. `reply_rps_including_drain` делит полученные ответы на полную продолжительность с ожиданием; это не максимальная устойчивая производительность сервера. Нагрузка на отправку достигла заявленных частот с отклонением менее 0,1%.

## Профилирование и оптимизация обработки аренд

CPU-профили сняты на том же ARM64-стенде с 100 000 аренд и прямыми продлениями 5 000 запросов/с. Профилирование включается только в сборке с тегом `loadtest` и переменной `GODHCP_LOAD_PROFILE=1`; HTTP-порт профилировщика 6060 слушает только loopback внутри изолированного контейнера. Производственная сборка не содержит этого обработчика.

```bash
GODHCP_LOAD_RESULTS="$PWD/output/load-profile" bash scripts/test-load-docker.sh \
  --case direct-renew-5000 --profile
GOTOOLCHAIN=go1.26.0 go tool pprof -top -cum \
  output/load-profile/direct-renew-5000.cpu.pprof
```

До оптимизации `pool.state.rebind` занимал 79,95% CPU-сэмплов: при каждом продлении линейно перебирался индекс всех MAC. Теперь прежний владелец определяется через IP → MAC за O(1). Операции восстановления из БД, карантина и возврата резерваций используют тот же согласованный индекс. Микротест `BenchmarkRenewAt100KLeases` на macOS ARM64/Apple M4 изменился с 474 474 нс/операцию до 64,38 нс/операцию (по 16 B и одной аллокации). Это локальный микротест пула, не измерение полного DHCP-запроса.

После удаления обхода следующий профиль показал 55,36% CPU в `UpsertLease`, включая 36,98% в `Tx.Commit`. Для прежней идентичности аренды добавлен подготовленный UPDATE: MAC, client-id, subnet и VLAN проверяются, неизменные индексы не перезаписываются. Метаданные relay и hostname по-прежнему обновляются; created_at сохраняется. При смене идентичности используется полный UPSERT. Новые записи relay и аренда фиксируются атомарно.

Оставшуюся цену отдельных commit уменьшает групповая обработка уже полученных датаграмм: очередь приёма ограничена 256 элементами, группа — 64 пакетами. Дополнительного ожидания для наполнения группы нет. Для SQLite группа использует одну транзакцию; ACK и callbacks выдаются только после успешного COMMIT. При ошибке все записи группы откатываются, ответы не отправляются, индекс пулов восстанавливается по зафиксированной БД. Если чтение БД тоже недоступно, новые запросы не обслуживаются до успешного восстановления индекса. WAL/synchronous=NORMAL сохранены; запись не заменена незащищённым кешем в памяти.

Промежуточные профили при одинаковой входящей нагрузке показали рост корректных ответов за окно 10 секунд плюс сбор: 7 290 (исходный профиль), 20 770 (индекс O(1)), 31 149 (SQL), 50 000 (групповой commit). Эти промежуточные прогоны выполнялись с профилированием и служат диагностике, а не итоговому сравнению задержек. Профили и отчёты находятся в `output/load-before-profile/`, `output/load-index-optimized-profile/`, `output/load-storage-optimized-profile/`, `output/load-batch-profile/`.

## Анализ хвоста задержек relay — 23 октября 2026

Исходные p99=136,26 мс не удалось повторить в точности: первый диагностический прогон на 30 секунд дал p99=5,76 мс, последующий на 120 секунд — 12,85 мс. Поэтому без трассы исходного запуска нельзя доказать причину именно того события. Найдены и исправлены два источника задержек в общем пути DHCP/relay.

1. Linux-транспорт вызывал `net.InterfaceByIndex` для каждой датаграммы. В используемой версии Go это полный запрос RTM_GETLINK через netlink, хотя обработчику нужно только имя одного интерфейса. CPU-профиль показал 23,15% сэмплов в этом вызове и 25,15% в фоновой маркировке GC. Linux-микротест: прежний вызов 17 220 нс, 43 813 B, 39 аллокаций; новый запрос `SIOCGIFNAME` на уже открытом UDP-сокете — 205,3 нс, 2 B, одна аллокация. Кеш не используется: переименование и повторное использование индекса не сохраняют устаревшее соответствие VLAN.
2. Checkpoint SQLite выполнялся в потоке commit. В диагностической runtime-трассе 68,47% суммарного времени системных вызовов пришлось на `Tx.Commit`; это доля ожидания системных вызовов, не доля CPU. После исправления интерфейсов оставались медленные commit до 41,30 мс. События commit пересекались с интервалами длинных ответов; ограничение CPU контейнера не срабатывало. Перенос автоматического checkpoint из commit в отдельный поток — документированный способ уменьшить этот хвост: [SQLite WAL](https://www.sqlite.org/wal.html#performance_considerations).

Теперь для стандартной дисковой SQLite-конфигурации отдельное соединение каждые 50 мс выполняет `wal_checkpoint(PASSIVE)`. Запись аренд сохраняет одно соединение и прежние транзакционные гарантии. Резервный автоматический checkpoint остаётся включён на 16 384 страницах (около 64 MiB при странице 4 KiB), если фоновая работа не успевает. Пользовательский DSN с `_pragma` сохраняет собственную политику. Для БД в памяти фоновый процесс не запускается. При закрытии хранилища процесс завершается, оба соединения закрываются. Ошибки checkpoint журналируются; автоматический механизм продолжает работать.

Это не жёсткий предел размера WAL: длительные читающие транзакции могут мешать checkpoint. WAL-файл также может сохранять прежний размер после повторного использования. В диагностике максимум размера был около 64,4 MiB. Режим `synchronous=NORMAL` сохранён: он защищает транзакционность, но не гарантирует сохранение последних commit при отключении питания. Он и ранее имел это ограничение. Некоторые барьеры записи остаются на пути commit; обещания нулевых выбросов нет.

### Контрольные двухминутные прогоны

Условия прежние: 4 общих vCPU, 2 GiB RAM, 100 000 аренд, SQLite, изолированный UDP-стенд. Включены диагностические записи медленных commit, GC и cgroup; CPU/runtime-профилирование выключено. Задержка по-прежнему считается от запланированного времени отправки, а не только от фактической отправки. Генератор дополнительно сообщает фактический RTT и опоздание отправки; массивы результатов выделяются заранее.

- До исправлений: relay 10 000 запросов/с, 1 200 000 ACK, p95 4,10 мс, p99 12,85 мс, p99 фактического RTT 12,20 мс; CPU сервера 106,82 с.
- Только исправление интерфейсов: relay 1 200 000 ACK, p95 2,35 мс, p99 4,68 мс; CPU 69,44 с.
- Оба исправления: relay 1 200 000 ACK, p95 1,67 мс, p99 2,51 мс, максимум 11,07 мс, p99 фактического RTT 2,01 мс; CPU 69,77 с. Ответов дольше 20 мс не было.
- Оба исправления: прямой DHCP 5 000 запросов/с, 600 000 ACK, p95 1,02 мс, p99 2,20 мс, p99 фактического RTT 1,69 мс. Сохранился всплеск до 110,01 мс, совпавший с commit 83,00 мс; 1 868 ответов (0,31%) заняли не менее 20 мс. Это ограничение результата, несмотря на хороший p99.

Во всех этих прогонах — ноль потерянных, некорректных и повторных ответов; все 100 000 аренд обновлены, IP/MAC и relay-метаданные проверены, `integrity_check=ok`. В двухминутном relay-прогоне число commit не короче 5 мс уменьшилось с 34 до одного (6,39 мс). Исходный результат 136 мс остаётся в истории отчётов; новый результат его не заменяет.

Диагностические артефакты лежат в `output/relay-tail-before/`, `output/relay-tail-120s-before/`, `output/relay-tail-trace/`, `output/relay-tail-ioctl/` и `output/relay-tail-checkpoint/`. Runtime-трассировка заметно исказила нагрузку и дала потери; этот прогон исключён из итоговых измерений.

```bash
GODHCP_LOAD_RESULTS="$PWD/output/relay-tail-checkpoint" bash scripts/test-load-docker.sh \
  --seconds 120 --case direct-renew-5000 --case relay-renew-10000 --diagnostics
# Для диагностики, не приёмки по задержкам:
GODHCP_LOAD_RESULTS="$PWD/output/relay-tail-trace" bash scripts/test-load-docker.sh \
  --seconds 60 --case relay-renew-10000 --trace --diagnostics
```

`--diagnostics` сохраняет интервалы commit явных транзакций аренд ≥5 мс (автокоммит одиночного UPDATE этим журналом не измеряется) и сэмплы cgroup/размера WAL. Генератор считает все ответы ≥20 мс, но сохраняет ограниченную выборку их временных меток (до 20 в секунду, максимум 1 000). Обработчики профиля/трассы и запись времени commit доступны только в сборке `loadtest`; в обычном бинарнике диагностических HTTP-обработчиков нет. Эти короткие виртуальные прогоны не заменяют испытания на реальном оборудовании и 24-часовую нагрузку.

Контроль без профилирования, трассы, журнала commit и GC (по 30 секунд) также прошёл без потерь: DHCP — 150 000 ACK, relay — 300 000 ACK. Точные процентили и контроль БД: [tail-final.json](../tests/load/results/arm64-2026-10-23-tail-final.json). Сводка двухминутных диагностических сравнений: [tail-diagnostics.json](../tests/load/results/arm64-2026-10-23-tail-diagnostics.json).

Проверки после исправлений: `go test -race -coverprofile=coverage.out ./...`, `go vet ./...`, Linux-тесты поиска и переименования интерфейса, 21 сетевая проверка (включая PCP и пересоздание контейнера), проверка лицензий. Покрытие — 72,86%. Дополнительно проверяется завершение фонового checkpoint, перенос данных в основной файл без закрытия БД и сохранность аренды после повторного открытия.

## Проверка увеличенного кеша — 26 октября 2026

**Полное устранение всплесков не подтверждено.** Увеличение SQLite page cache до 32 MiB улучшило результат прямого DHCP в приведённом сравнении, но не устранило длинные ответы relay. Это настройка кеша, а не доказанное исправление всех задержек диска/планировщика.

В сохранённой runtime-трассе без strace (`output/dhcp-spike-flight-only/direct-renew-5000.flight.trace`) пойман commit 48,46 мс: интервал 47,57 мс приходится на системный вызов записи из `modernc.org/libc.Xpwrite` в пути SQLite WAL. Следовательно, длительность commit нельзя автоматически приписывать одному fsync или сборщику мусора. В отдельном 60-секундном диагностическом контроле паузы GC сервера были меньше 2 мс, генератора — меньше 0,04 мс, но длинные ответы сохранились. Перенос БД с host bind mount на Linux-диск также не исключил всплески. Точная первопричина задержки системного вызова на уровне ядра/виртуализации не установлена; исходный commit 83 мс собственной трассой не сопровождался.

При стандартной конфигурации теперь задаётся `cache_size=-32768`: до 32 MiB страничного кеша на соединение. SQLite выделяет его по мере необходимости; два соединения не означают немедленного выделения всех 64 MiB. Пользовательский URI DSN с `_pragma` сохраняет свои параметры. Настройка не отменяет запись WAL, commit перед ACK, режим `synchronous=NORMAL` или автоматический checkpoint. Описание семантики: [SQLite PRAGMA cache_size](https://www.sqlite.org/pragma.html#pragma_cache_size).

### Свежие измерения без диагностических накладных расходов

Условия: по 120 секунд, 100 000 аренд, контейнер с 4 общими vCPU и 2 GiB RAM, сервер GOMAXPROCS=4, генератор GOMAXPROCS=1. SQLite расположен в прежнем каталоге результатов, примонтированном с macOS (`fuseblk`); внешний трафик отключён. Ни runtime/CPU/IO-трассировка, ни flight recorder, ни журналы commit/GC не включались. На macOS применялся `caffeinate -i` на время команды для предотвращения простоя со сном. Измеряется задержка от запланированной отправки.

- Кеш 32 MiB, DHCP 5 000 запросов/с: 600 000 корректных ACK, p95 0,96 мс, p99 1,53 мс, максимум 8,79 мс; ответов ≥20 мс нет.
- Кеш 32 MiB, relay 10 000 запросов/с: 1 200 000 корректных ACK, p95 1,66 мс, p99 10,85 мс, максимум 295,71 мс; 9 517 ответов ≥20 мс (0,79%). У самого медленного ответа фактический RTT 294,68 мс: задержка не объясняется только опозданием отправки генератора.
- Контроль DHCP с кешем 2 000 KiB: 600 000 корректных ACK, p95 0,98 мс, p99 1,73 мс, максимум 58,43 мс; 709 ответов ≥20 мс. Контроль собран через Go `-overlay`, меняющий только значение cache_size; остальные изменения и параметры стенда те же.

Во всех трёх случаях нет потерь, некорректных и повторных ответов. Обновление всех 100 000 аренд, IP/MAC, relay-метаданные и `PRAGMA integrity_check=ok` проверены. Диагностический relay-прогон 25 октября с кешем 32 MiB также завершился без потерь, но дал p99 177,18 мс и максимум 592,07 мс. Он не используется вместо свежего контроля, однако является дополнительным контрпримером заявлению, что кеш устранил проблему.

Один контроль до/после не доказывает причинного устранения редкого события; даже кеш 2 000 KiB в свежем DHCP-прогоне не дал задержки 110 мс. Значение `target_met=true` в JSON проверяет прежние требования к частоте, p95, корректности и БД. Оно **не** означает прохождение проверки максимальной задержки или исчезновение всплесков.

Отчёты: [кеш 32 MiB](../tests/load/results/arm64-2026-10-26-cache32-final.json), [контроль 2 000 KiB](../tests/load/results/arm64-2026-10-26-cache2-control.json), [сводный вывод](../tests/load/results/cache-validation-2026-10-26.json). Детальные артефакты остаются в `output/tail-final-oct26/` и `output/tail-cache2-control-oct26/`.

Для повторения текущей сборкой:

```bash
GODHCP_LOAD_RESULTS="$PWD/output/tail-final" bash scripts/test-load-docker.sh \
  --seconds 120 --case direct-renew-5000 --case relay-renew-10000 --storage host
```

На macOS перед `bash` можно поставить `caffeinate -i`. Режим `--storage native` помещает БД на Linux-диск контейнера и после остановки сервера копирует основной файл в результаты; это отдельный сценарий, а не незаметная замена хранилища в сравнении. `--io-trace` включает strace для fsync/fdatasync/pwrite64 и предназначен только для диагностики. `--flight` включает диагностику и сохраняет первую трассу операции хранения ≥20 мс после стартовых пяти секунд. Старые снимки этой же проверки удаляются перед новым прогоном, чтобы не принять их за новый захват. Журнал различает commit и checkpoint, включая число кадров WAL/скопированных кадров. Генератор сохраняет параметры самого медленного ответа независимо от ограниченной выборки остальных медленных ответов.

Итоговые проверки этой рабочей копии прошли: `GOTOOLCHAIN=go1.26.0 go test -race -coverprofile=coverage.out ./...`, тесты storage/cmd с тегом `loadtest`, `go vet`, проверка лицензий и все 21 сетевой сценарий (PCP, DHCP lifecycle и пересоздание контейнера). Покрытие полным запуском — 70,87%, порог 70% выполнен. Проверены сохранение cache_size при замене соединения и сохранение пользовательского значения кеша. Эти зелёные проверки функциональной корректности не отменяют зафиксированную проблему хвоста relay.
