# Архитектура

Один процесс `godhcp` совмещает четыре контура.

1. UDP-сервер (`internal/server`) читает DHCPv4, передаёт пакет в `core.Service.Handle` и отправляет ответ.
2. Ядро (`internal/core`) выбирает подсеть, выделяет адрес и собирает OFFER/ACK/NAK.
3. Хранилище (`internal/storage`) держит аренды в SQLite или PostgreSQL. Пул в памяти — индекс поверх базы.
4. HTTP (`internal/api`) отдаёт REST, Swagger и собранный React-интерфейс из `internal/webui`.

Прямой запрос приходит на интерфейс вида `eth0.10`. VLAN берётся из имени интерфейса или из вспомогательных данных пакета. Дальше ядро ищет подсеть с этим VLAN и выделяет адрес. В ответ кладётся PCP из `vlans[].priority`, чтобы отправитель мог выставить 802.1p.

Запрос через relay узнаётся по ненулевому `giaddr`. Ответ уходит unicast на `giaddr:67`. Поле `giaddr` в пакете не подменяется адресом сервера: так требует RFC 2131. `siaddr` — это `next_server` или server-id.

Порядок источников VLAN:

1. sub-option 5 (link-selection) — подсеть, в которую попадает адрес;
2. sub-option 1 (Circuit ID) — regex-парсер;
3. `giaddr` — запись доверенного relay;
4. `default_vlan` / `default_pool`.

Распознанный, но не настроенный VLAN останавливает поиск. Неразобранный Circuit ID проваливается дальше. Опция 82 копируется в ответ байт в байт, включая вложенный sub-option 152.

Выдача адреса идёт в транзакции хранилища. Резервация важнее динамического пула. Строгий REQUEST не подменяет запрошенный адрес другим. Неудачный ping-check и DECLINE помечают адрес занятым до истечения удержания.

`SIGHUP` и `POST /api/v1/config/reload` вызывают `Service.Apply`: схема проверяется, каталог подсетей переписывается, слушатели UDP и HTTP не пересоздаются.
