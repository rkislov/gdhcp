# Автоматический кластер GoDHCP

© 2026 Кислов Роман Сергеевич. Apache License 2.0.

Режим реализован в текущих исходниках и пока считается экспериментальным. Он запускается параметром `-cluster-config`, использует три Raft-реплики с mTLS и один активный набор DHCP/API/DDNS. Режим включён в пакеты и бинарники начиная с версии 0.1.15.

На изолированном Linux-стенде проверены три настоящих демона, DHCPv4, DHCPv6 напрямую и через relay, разрыв peer TCP, fencing, перенос service IPv4/IPv6 и продление прежних адресов с сохранением DUID. Реальный Samba AD принимает A/PTR-обновления нового лидера и удаление прежнего имени. При потере кворума выдача обоих протоколов прекращается, VIP снимаются.

## Подготовка

Нужны три Linux-узла одной сервисной L2-сети, одинаковая сборка GoDHCP, одинаковые имена интерфейсов в общей политике, синхронизация часов и TCP-связность между всеми peer-адресами. Пример использует DHCP-A `192.0.2.11`, DHCP-B `.12`, DHCP-C `.13`, VIP `192.0.2.10/24`, интерфейс `ens192`. Замените документационные адреса своими. VLAN 112 не изменяется.

Один узел активен, остальные держат Raft. Веб/API на резервных узлах не запущен. Пользователи подключаются к service IP. На DHCP relay укажите VIP. `server.server_id` всех узлов равен VIP, чтобы unicast Renew после переноса попадал новому активному узлу.

Raft хранит журнал, снимки, аренды IPv4/IPv6, DUID, конфигурацию, DDNS owner и очередь DNS-намерений в локальном каталоге. PostgreSQL для режима не нужна. Обычный `database.dsn` не используется как источник аренд — локальный каталог подсетей создаётся в памяти и восстанавливается из общей политики. **Автоматического импорта действующих SQLite/PostgreSQL аренд в Raft нет. Не включайте режим поверх рабочей сети с пустым журналом.** Первое включение допускается для нового выделенного пула или после отдельно проверенного переноса/карантина старых аренд.

Установите отдельные TLS-сертификаты из внутреннего CA. Каждый сертификат имеет EKU `serverAuth,clientAuth`, DNS SAN своего имени и ровно один URI SAN. Для кластера `office` и узла `a` URI равен `spiffe://godhcp/cluster/office/node/a`. Узлам b/c выдаются свои URI. CA key на узлы не передаётся. Стандартные настройки API TLS независимы от peer TLS. Peer-обмен требует TLS 1.3. Запрещён обход проверки сертификата.

Каталог Raft содержит хэши паролей и API-ключи. Защитите его и резервные копии. JWT secret, LDAP bind password/CA path, DSN БД, DDNS keytab/key_file и локальные listener/TLS-пути не реплицируются — подготовьте их на каждом узле. При необходимости общих веб-сессий задайте одинаковый JWT secret.

## Манифест

На узле a создайте `/etc/godhcp/cluster.yml` с правами 0600 для пользователя службы.

```yaml
id: office
node: a
listen: 192.0.2.11:8444
data_dir: /var/lib/godhcp/cluster
bootstrap: true
ca: /etc/godhcp/cluster-tls/ca.pem
cert: /etc/godhcp/cluster-tls/a.pem
key: /etc/godhcp/cluster-tls/a.key
peers:
  - id: a
    address: 192.0.2.11:8444
    hostname: dhcp-a.example.net
  - id: b
    address: 192.0.2.12:8444
    hostname: dhcp-b.example.net
  - id: c
    address: 192.0.2.13:8444
    hostname: dhcp-c.example.net
fence: [/usr/local/sbin/godhcp-fence-peer]
ip_up: [/usr/local/sbin/godhcp-cluster-ip, up, ens192, 192.0.2.10/24]
ip_down: [/usr/local/sbin/godhcp-cluster-ip, down, ens192, 192.0.2.10/24]
```

На b/c измените `node`, `listen`, `cert`, `key`, задайте `bootstrap: false`. Список peers и его порядок сохраняйте одинаковыми. Bootstrap разрешён только на одном узле и только для первого создания кластера. После первого запуска установите false и на a. Существующий журнал не переинициализируется.

`identity.json` связывает каталог с node-id и topology. Несогласованное повторное использование каталога отклоняется. Нельзя копировать каталог одного узла другому, удалять `identity.json`, менять peers для принудительного восстановления кворума. Динамическое добавление/удаление участников пока не поддержано.

В обычном `/etc/godhcp/config.yml` настройте сеть, пользователей и локальные секреты. Пример дополнения к полной конфигурации.

```yaml
server:
  listen: ":67"
  server_id: 192.0.2.10
ha:
  enabled: false
api:
  listen: ":8181"
```

Первый лидер инициализирует общую политику из своего YAML. На первоначальном запуске общая часть YAML должна совпадать на всех узлах, поскольку первый лидер не обязательно является bootstrap-узлом. После инициализации источником общей политики становится Raft. Старт и reload объединяют её с локальными секретами и listener-настройками.

## Fencing и service IP

Пошаговые требования, команды и приёмка для Proxmox, VMware, Hyper-V, KVM/libvirt, IPMI, Redfish и PDU приведены в [отдельной инструкции по fencing](fencing.md). Готовые адаптеры для VM, IPMI и Redfish устанавливаются из `scripts/godhcp-fence-peer` и Windows PowerShell-обработчиков; конфигурационные шаблоны находятся в `deploy/fencing`. PDU пока требует собственного адаптера.

Все три hook-команды обязательны, запускаются напрямую без shell, с таймаутом 20 секунд. Ненулевой exit code блокирует активацию. `fence` получает node-id последним аргументом. Hook обязан завершиться успешно **только после подтверждённой остановки или изоляции** прежнего DHCP/API/DDNS, включая уже запущенные DNS-команды и service IP. Потеря ping/SSH не является подтверждением. Предпочтительны BMC/гипервизор или проверенное сетевое fencing. Если такой механизм недоступен, кластер остановит переключение.

Для гипервизора или управляющего шлюза доступен готовый SSH-транспорт, описанный в инструкции по fencing. Альтернативный собственный адаптер для доступного по отдельной управляющей сети Linux-узла должен вызывать заранее установленную команду принудительной остановки/блокировки unit и удаления VIP. Адреса сопоставляйте с фиксированным списком node-id. Используйте `BatchMode=yes`, `StrictHostKeyChecking=yes`, заранее проверенные known_hosts и ограниченный ключ. Если SSH недоступен, адаптер должен возвращать ошибку. Этот способ сохраняет безопасность, но не обеспечивает доступность при потере управляющей сети. Не заменяйте fencing скриптом `exit 0`.

Установите предоставленный IPv4/IPv6-адаптер.

```sh
sudo install -m 0755 scripts/godhcp-cluster-ip /usr/local/sbin/godhcp-cluster-ip
```

Требуются Python 3, iproute2 и iputils arping (Debian — `python3 iproute2 iputils-arping`, Rocky — `python3 iproute iputils`). Адаптер добавляет выделенный VIP и отправляет gratuitous ARP. При остановке удаляет только указанный адрес/префикс. Другие адреса интерфейса сохраняются. VIP не должен автоматически назначаться сетевым менеджером при reboot. Не используйте в качестве VIP основной адрес хоста.

При включённом DHCPv6 общий DUID сохраняется в Raft. Приложенный адаптер поддерживает глобальный/ULA IPv6 на Ethernet: ожидает завершения DAD, отклоняет конфликт и отправляет три unsolicited Neighbor Advertisement с Override для обновления кэша соседей. Для dual stack задайте ip_up/ip_down как абсолютные пути к двум локальным скриптам, последовательно вызывающим адаптер для IPv4 и IPv6. При ошибке up скрипт обязан вернуть ошибку, down должен убирать оба адреса. Сам координатор выполняет down после неудачного up. Без Neighbor Advertisement relay может продолжать отправлять unicast на MAC прежнего владельца — это обнаружено и исправлено на стенде. RA обеспечивает маршрутизатор.

Для dual stack создайте два root-owned исполняемых скрипта. Например, `/usr/local/sbin/godhcp-ip-up`.

```sh
#!/bin/sh
set -eu
/usr/local/sbin/godhcp-cluster-ip up ens192 192.0.2.10/24
/usr/local/sbin/godhcp-cluster-ip up ens192 2001:db8:10::10/64
```

И `/usr/local/sbin/godhcp-ip-down`, который пытается снять оба адреса даже при ошибке одной операции.

```sh
#!/bin/sh
status=0
/usr/local/sbin/godhcp-cluster-ip down ens192 192.0.2.10/24 || status=$?
/usr/local/sbin/godhcp-cluster-ip down ens192 2001:db8:10::10/64 || status=$?
exit "$status"
```

В манифесте укажите `ip_up: [/usr/local/sbin/godhcp-ip-up]` и `ip_down: [/usr/local/sbin/godhcp-ip-down]`. Адреса замените своими. На relay используйте соответствующий service IPv6. Не используйте link-local или multicast как переносимый service IP.

## systemd и первый запуск

Сначала остановите прежние самостоятельные экземпляры GoDHCP. Запускать одновременно standalone и cluster с пересекающимися пулами нельзя.

Проверьте файлы на каждом узле.

```sh
sudo /usr/bin/godhcp -validate -config /etc/godhcp/config.yml -cluster-config /etc/godhcp/cluster.yml
```

В drop-in `systemctl edit godhcp` переопределите команды запуска установленного unit. Для приведённого hook, управляющего адресами напрямую, добавьте CAP_NET_ADMIN к существующим возможностям. Пользователь `godhcp` должен иметь доступ к Raft-каталогу, сертификатам и своему SSH/BMC механизму. Не предоставляйте произвольный root-shell через hooks.

```ini
[Service]
ExecStartPre=
ExecStartPre=/usr/bin/godhcp -validate -config /etc/godhcp/config.yml -cluster-config /etc/godhcp/cluster.yml
ExecStart=
ExecStart=/usr/bin/godhcp -config /etc/godhcp/config.yml -cluster-config /etc/godhcp/cluster.yml -control-socket /run/godhcp/control.sock
AmbientCapabilities=CAP_NET_BIND_SERVICE CAP_NET_ADMIN CAP_NET_RAW
CapabilityBoundingSet=CAP_NET_BIND_SERVICE CAP_NET_ADMIN CAP_NET_RAW
KillMode=control-group
```

CAP_NET_RAW требуется arping и ICMPv6 Neighbor Advertisement. KillMode=control-group обязателен для очистки дочерних DNS/hook-процессов при завершении службы. Рабочий запуск должен выполняться под systemd либо эквивалентным supervisor, который уничтожает всю группу процессов, а не только PID godhcp. Настройку fence-адаптера проверьте от имени службы с её реальными правами. Манифест и hook-программы не должны быть доступны для записи непривилегированным пользователям. Подготовьте каталог `install -d -o godhcp -g godhcp -m 0700 /var/lib/godhcp/cluster`.

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now godhcp
sudo journalctl -u godhcp -f
```

Запустите все три узла. `READY=1` обозначает готовность координатора, в том числе на follower. Это не означает активную выдачу DHCP. Активность подтверждается `cluster active`, наличием ровно одного VIP, `/readyz` на service IP и проверкой клиента. После сбоя workload запускается повторно только через полный цикл активации. При ошибке cleanup координатор завершается, не выдавая локальную повторную активацию за безопасную.

## Работа через веб и reload

Откройте service IP на 8181. Изменения общей политики сохраняются в Raft. Поле `cluster_revision` в YAML/JSON не удаляйте — оно предотвращает перезапись новой конфигурации устаревшей правкой. При конфликте загрузите свежую конфигурацию и повторите изменения. Локальный YAML не обновляется веб-сохранением в кластерном режиме.

Локальные listener-настройки и секреты изменяются в YAML каждого узла с последующим перезапуском. Попытка изменить их через общую политику отклоняется. На активном узле reload загружает committed policy. На follower control socket/API не запущены, поэтому `systemctl reload` может завершиться ошибкой — для изменения локальных настроек нужен restart. Изменение DHCPv6 требует перезапуска слушателя. Не перезапускайте два Raft-узла одновременно.

Неприменённая конфигурация блокирует ответы DHCPv4 до успешного reload. Полноценная горячая смена всех listener-настроек и кластерная панель статуса пока отсутствуют.

## Приёмочный стенд и границы проверки

Из корня исходников выполните `bash scripts/test-cluster-docker.sh`. По умолчанию стенд также поднимает одноразовый Samba AD с тестовым keytab. `GODHCP_CLUSTER_SAMBA=0` отключает только Samba-проверки. Docker должен работать, стенд создаёт привилегированный **изолированный** контейнер `--network none` и network namespaces. Не запускайте `cluster_lab.py` непосредственно на рабочем сервере.

Результаты находятся в `output/cluster-lab`: `report.json`, журналы a/b/c и pcap получения/продления. Стенд имеет собственный тестовый fencing, который уничтожает все процессы в namespace, включая дочерние DNS/IP-команды, и снимает оба VIP. Его нельзя переносить в рабочую систему как BMC-адаптер.

Проверено на Linux ARM64 в Docker 19 ноября 2026 года: три настоящих процесса, mTLS/Raft, DORA, изоляция peer TCP при работающей клиентской сети, fencing/VIP, продление IPv4, DHCPv6 direct/relay с теми же адресами и DUID, обновление Samba A/PTR новым лидером, возврат изолированной реплики с прежним журналом, второе переключение после SIGKILL и отсутствие DHCPv4/v6-ответов без большинства. Тесты `go test -race` дополнительно проверяют возврат реплики, снимки, IPv6, очередь DDNS, версии конфигурации и отрицательные TLS-сценарии. Они не заменяют проверки физического fencing, systemd reboot, разных видов асимметричной изоляции, длительной нагрузки и восстановления после отказа дисков в вашей инфраструктуре.

При потере большинства не создавайте новый пустой кластер. Сохраняйте каталоги всех узлов и восстанавливайте минимум две совместимые реплики. Восстановление из старого снимка с потерей подтверждённых аренд требует отдельного карантина адресов. Кластерные WAL и snapshots не копируются между работающими узлами вручную.
