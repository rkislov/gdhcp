# Руководство администратора GoDHCP

© 2026 Кислов Роман Сергеевич. Apache License 2.0.

Установка и обслуживание DHCPv4-сервера на Linux, экспорт настроек ISC DHCP (`isc-dhcp-server` / `dhcpd`) и подготовка перехода на GoDHCP. Примеры рассчитаны на Debian/Ubuntu с systemd. Адреса, имена интерфейсов и пути необходимо заменить на свои. Команды администрирования выполняются в root-сессии Bash (`sudo -i`).

Для ежедневной работы в браузере см. [пошаговую инструкцию по веб-интерфейсу](web-guide.md): вход, поиск устройства, постоянный IP для принтера и проверка результата.

## Изменения версии 0.1.9

Исправлен автоматический доступ `anonymous` с правами администратора: если `api.auth.users` и `api.auth.api_keys` пусты, защищённый API возвращает 401. Для веб-входа настройте пользователя и JWT secret в YAML до обновления, затем перезапустите службу. Действующая сохранённая сессия настроенного пользователя по-прежнему позволяет входить без повторного ввода пароля. Порт по умолчанию для веб-интерфейса и API - 8181; явно заданный `api.listen` сохраняет своё значение. Подробности: [обновление до 0.1.9](upgrade-v0.1.9.md).

## Состояние текущей версии

В версии 0.1.1 исправлены четыре ошибки DHCP-ядра: OFFER/ACK отправляется только после успешного сохранения аренды, REQUEST не меняет подсеть по запрошенному IP при известном входном VLAN, RELEASE/DECLINE проверяют владельца действующей аренды, повторный DISCOVER сохраняет состояние и срок bound-аренды. Добавлены регрессионные тесты. Выдача, reload и очистка аренд согласованы внутри одного процесса.

В версии 0.1.2 исправлены ещё четыре сетевые ошибки: начальные OFFER/ACK доставляются клиентам без broadcast-флага, прямой NAK всегда отправляется broadcast с нулевым ciaddr, BOOTREPLY игнорируется, явное имя интерфейса из `vlans[].interface` участвует в выборе VLAN. Ошибки отправки UDP теперь попадают в журнал. Для начальных ответов используется разрешённый RFC 2131 §4.1 broadcast fallback: обычный UDP-сокет не умеет отправлять кадр непосредственно на MAC ещё не настроенного клиента. Продление остаётся unicast, ответы relay идут на giaddr:67.

В версии 0.1.3 запуск systemd переведён на `Type=notify`: готовность подтверждается после открытия DHCP, HTTP, metrics и управляющего сокета. Ошибка bind завершает процесс с ненулевым кодом; `Restart=on-failure` позволяет повторить запуск. Reload через приватный Unix-сокет ждёт применения конфигурации и возвращает ошибку при некорректном YAML. Стартовые настройки больше не перезаписываются из обработчика SIGHUP.

На изолированном Docker-стенде Linux ARM64 выполнена 21 проверка: получение и продление адресов, настоящий 802.1Q, ISC relay с Option 82, автоматическое продление ISC dhclient, перезапуск процесса и пересоздание контейнера с сохранённой SQLite. Повторный запуск описан ниже. Испытания не означают совместимость с ISC failover или проверку всех сетевых сценариев; перед заменой рабочего DHCP нужны приёмочные испытания в вашей сети.

Дополнительно учитывайте:

- `ping_check` не подключён в точке запуска; включение параметра пока не защищает от конфликтов IP.
- Создание чистой базы PostgreSQL содержит ошибки миграции; для стенда используйте SQLite.
- `raw_vlan` не подключён. Для локальных VLAN нужны заранее созданные ОС интерфейсы. PCP на Linux работает через SO_PRIORITY и заранее настроенную egress-qos-map; см. [настройку PCP](vlans.md#pcp-на-linux).
- `server.interfaces` не является ограничением приёма UDP-пакетов. Ограничивайте доступ сетевыми правилами и выбором адреса `server.listen`.
- `/readyz` проверяет базу, но не прохождение DHCP через сеть. В systemd готовность при запуске дополнительно требует открытия всех слушателей.
- DHCPv6, DDNS и обмен состоянием ISC failover не реализованы. `ha` делит клиентов по хэшу; два экземпляра с пересекающимися пулами могут выдать одинаковый IP.

Ниже приведена процедура подготовки и стендовой проверки. Переключение рабочей сети выполняйте после оценки оставшихся ограничений и приёмочных испытаний.

## Установка пакета для дистрибутива

Подготовлены пакеты версии 0.1.9 для Linux amd64 и arm64. Для Debian/Ubuntu используйте `.deb`, для RHEL, Rocky Linux, AlmaLinux и Fedora - `.rpm`. Это статический Go-бинарный файл без зависимости от glibc; установка пакетов проверяется отдельно от работы DHCP в реальной сети. Архив `.tar.gz` предназначен для ручной установки, включая другие Linux-дистрибутивы.

На машине со сборками проверьте контрольные суммы, затем передайте пакет нужной архитектуры на сервер:

```bash
cd dist/releases/0.1.9
sha256sum -c SHA256SUMS
```

Debian/Ubuntu, amd64:

```bash
apt install ./godhcp_0.1.9_linux_amd64.deb
```

RHEL-подобные системы/Fedora, amd64:

```bash
dnf install ./godhcp_0.1.9_linux_amd64.rpm
```

Для ARM64 выберите файл с `arm64`; внутри RPM эта архитектура обозначена как `aarch64`. Архитектуру хоста проверьте через `uname -m`: `x86_64` соответствует amd64, `aarch64` соответствует arm64.

Пакет устанавливает `/usr/bin/godhcp`, unit `/usr/lib/systemd/system/godhcp.service`, пример `/etc/godhcp/config.yml.example`, документацию и PDF в `/usr/share/doc/godhcp/`. Скрипт установки создаёт системного пользователя `godhcp` и каталоги. Служба не запускается и не включается автоматически; активный конфиг и секреты не создаются. При обновлении существующая служба автоматически не перезапускается, поэтому новый бинарный файл начнёт обслуживать сеть после запланированного перезапуска.

При новой установке скопируйте пример, если ещё не подготовлен импортированный конфиг:

```bash
test -f /etc/godhcp/config.yml || \
  install -m 0640 -o godhcp -g godhcp \
  /etc/godhcp/config.yml.example /etc/godhcp/config.yml
```

Настройте адреса, интерфейсы и аутентификацию по разделам ниже. В пакетном примере DHCP отключён через `server.listen: "-"`; замените значение на `":67"` перед сетевыми испытаниями. Затем проверьте конфиг и выполните запуск через systemd.

## Ручная установка бинарного файла

На машине сборки нужен Go 1.26 или новее. В корне проекта:

```bash
go version
go test ./...
go vet ./...
make build
./bin/godhcp version
```

Для Linux amd64 при сборке на другой ОС:

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o godhcp-linux-amd64 ./cmd/godhcp
```

Если выбран пакет, пропустите ручную установку и создание пользователя. Для архива распакуйте его в отдельный каталог: `tar -xzf godhcp_0.1.9_linux_amd64.tar.gz`. В архиве бинарный файл называется `godhcp`, рядом лежат unit, пример конфига, документация и PDF. На целевом Linux установите подходящий бинарный файл и создайте каталоги:

```bash
# Для бинарного файла из архива укажите godhcp вместо godhcp-linux-amd64.
install -m 0755 godhcp-linux-amd64 /usr/bin/godhcp
useradd --system --home-dir /var/lib/godhcp --shell /usr/sbin/nologin godhcp
install -d -m 0750 -o godhcp -g godhcp /etc/godhcp /var/lib/godhcp
```

Если пользователь уже существует, повторно создавать его не нужно. `version` выводит версию и завершает работу; DHCP-порт не открывается.

## Экспорт настроек из ISC DHCP

### Найти действующую конфигурацию

У ISC DHCP конфигурация хранится в текстовом `dhcpd.conf` и подключаемых файлах `include`. Для переноса нужен этот набор файлов; база `dhcpd.leases` хранит выданные аренды отдельно. Параметры `-cf` и `-lf` задают альтернативные пути. См. [руководство ISC dhcpd](https://kb.isc.org/docs/isc-dhcp-44-manual-pages-dhcpd).

На действующем сервере выполните:

```bash
systemctl status isc-dhcp-server --no-pager
systemctl cat isc-dhcp-server
ps -ww -C dhcpd -o args=
```

В некоторых дистрибутивах служба называется `dhcpd`: замените имя в командах. Зафиксируйте основной конфиг, путь аренд, интерфейсы, chroot и способ запуска. В Debian/Ubuntu обычно используются `/etc/dhcp/dhcpd.conf`, `/var/lib/dhcp/dhcpd.leases` и `/etc/default/isc-dhcp-server`; фактические параметры процесса имеют приоритет.

Просмотрите включения, затем откройте найденные файлы и их вложенные включения:

```bash
rg -n '^\s*include\s+' /etc/dhcp
```

Если `rg` не установлен, используйте `grep -R -n 'include' /etc/dhcp`. Поиск служит подсказкой: проверьте также абсолютные пути вне `/etc/dhcp`, ссылки и файлы внутри chroot. Запретите параллельное изменение конфигурации на время экспорта.

### Сохранить исходные файлы

Следующий пример архивирует `/etc/dhcp`, не останавливая действующий DHCP:

```bash
umask 077
export_dir="/root/isc-dhcp-export-$(date +%Y%m%d-%H%M%S)"
install -d -m 0700 "$export_dir"
tar -czf "$export_dir/settings.tar.gz" -C / etc/dhcp
systemctl cat isc-dhcp-server > "$export_dir/service.txt"
ps -ww -C dhcpd -o args= > "$export_dir/process.txt"
if test -f /etc/default/isc-dhcp-server; then
  cp -a /etc/default/isc-dhcp-server "$export_dir/isc-dhcp-server.defaults"
fi
if test -f /var/lib/dhcp/dhcpd.leases; then
  cp -a /var/lib/dhcp/dhcpd.leases "$export_dir/dhcpd.leases.snapshot"
fi
sha256sum "$export_dir/settings.tar.gz" > "$export_dir/settings.sha256"
```

Если включения находятся вне `/etc/dhcp`, включите их в команду `tar` отдельными путями относительно `/`, например `etc/dhcp opt/company/dhcp`. Архив должен содержать каждый реально используемый файл. Скопируйте отдельно внешние цели символических ссылок, если они не попали в архив. Для службы `dhcpd` скорректируйте и команды, сохраняющие описание службы.

Копия `dhcpd.leases` работающего сервера — предварительный снимок для анализа. Финальную копию для отката сохраните после остановки ISC DHCP в согласованное окно. Файлы экспорта могут содержать ключи TSIG, адреса и MAC клиентов: храните их с ограниченным доступом.

### Преобразовать экспорт в YAML GoDHCP

Предпочтительный вариант — выполнить импорт на исходном сервере, где доступны все исходные пути. Для этого достаточно скопировать бинарный файл GoDHCP: команда `import-dhcpd` не запускает DHCP-сервер и не меняет исходные файлы.

Сначала проверьте исходный конфиг самим ISC DHCP. Ключ `-t` проверяет синтаксис без сетевого обслуживания:

```bash
dhcpd -4 -t -cf /etc/dhcp/dhcpd.conf
```

Затем выполните преобразование, используя каталог экспорта из предыдущего шага:

```bash
/usr/bin/godhcp import-dhcpd \
  -in /etc/dhcp/dhcpd.conf \
  -out "$export_dir/godhcp-imported.yml" \
  2> "$export_dir/import.log"
```

Проверьте код завершения сразу после команды (`echo $?`), затем прочитайте **весь** `import.log`. При ненулевом коде не используйте результат. Строки `read:` перечисляют прочитанные файлы; `warning:` указывают на потери или ограничения переноса. Сравните этот перечень с составом архива. Нулевой код означает, что преобразование удалось, но не гарантирует эквивалентность поведения серверов.

```bash
cat "$export_dir/import.log"
/usr/bin/godhcp -validate -config "$export_dir/godhcp-imported.yml"
```

Если импорт выполняется на отдельной машине, сохраните структуру каталогов. Относительные `include` GoDHCP ищет относительно файла, содержащего включение; абсолютные пути продолжат ссылаться на исходные абсолютные адреса файлов. Распаковывайте архив в изолированной машине или контейнере с нужными путями либо исправьте пути в рабочей копии. Не распаковывайте чужой `/etc/dhcp` поверх действующей конфигурации другого сервера.

Импорт раскрывает вложенные включения до 32 уровней, отвергает циклы и пропускает повторное включение одного файла. Если ISC использует повторное включение в разных областях или относительные пути с другой базой разрешения, сравните результат вручную.

### Проверить полноту переноса

Автоматически переносятся IPv4-подсети, первый диапазон `range` каждой подсети, резервации `hardware ethernet` + `fixed-address`, поддерживаемые опции, сроки аренды, `next-server` и `filename`. `group` и `shared-network` переносят часть общих параметров в подсети; семантика общей физической сети автоматически не восстанавливается.

Обязательно проверьте:

- **Все диапазоны.** Второй и последующие `range` не переносятся. Не объединяйте диапазоны через занятые адреса; модель текущей версии допускает один динамический диапазон на подсеть. `range dynamic-bootp` требует ручной обработки.
- **Опции и наследование.** Сверьте шлюз, DNS, домен, NTP, PXE и vendor options для каждой подсети. Глобальные опции и локальные переопределения могут преобразовываться иначе; глобальные `next-server` и `filename` не следует считать перенесёнными без проверки.
- **Резервации.** Сверьте количество, MAC, IP и принадлежность подсети. Из списка `fixed-address` берётся первый адрес; имена вместо IPv4 требуют ручной обработки. Настройки внутри `host`, кроме поддержанных полей, могут быть потеряны.
- **Политики.** `pool` с allow/deny, `class`/`subclass`, условия и выражения не преобразуются в эквивалентные правила GoDHCP. Часть конструкций пропускается с предупреждением; вручную сопоставьте исходные блоки с YAML.
- **Failover и DDNS.** Настройки ISC failover, TSIG и динамические DNS-обновления не переносятся как работающие функции.
- **Сеть.** Задайте реальные интерфейсы, VLAN, доверенные relay, `giaddr`, Circuit ID и `server_id`. Импорт не восстанавливает сетевую топологию. `server_id` должен быть адресом самого DHCP-сервера, доступным клиентам для продления; автоматически выбранный адрес шлюза может не подходить.
- **Доступ к управлению.** Импортированный YAML не содержит пользователей и API-ключей. До запуска настройте аутентификацию: один `jwt_secret` не закрывает API.

**Действующие аренды из `dhcpd.leases` не импортируются.** YAML переносит конфигурацию, а не состояние выдачи. Нельзя запускать новый сервер с пустой базой и тем же пулом поверх ещё действующих аренд: он может повторно выдать занятые IP. Нужен отдельный план сохранения занятости либо проверенный свободный диапазон, исключённый из выдачи ISC. Автоматической команды импорта аренд в этой версии нет.

Передайте на целевую машину исходный архив, `godhcp-imported.yml` и `import.log` защищённым способом. Сохраните исходную копию YAML, редактируйте отдельный рабочий файл `/etc/godhcp/config.yml`.

## Настройка GoDHCP на стенде

Для первого испытания используйте один заранее настроенный VLAN или одну изолированную подсеть. Не подключайте стенд к рабочему широковещательному сегменту DHCP.

Пример `/etc/godhcp/config.yml` для интерфейса `eth0`, которому ОС уже назначила `192.168.50.2/24`:

```yaml
server:
  listen: ":67"
  server_id: 192.168.50.2
  interfaces:
    - name: eth0
      mode: access
      vlan: 50
  authoritative: true
  ping_check: false
  manage_links: false
  lease_default: 1h
  lease_max: 24h
database:
  driver: sqlite
  dsn: /var/lib/godhcp/leases.db
api:
  listen: "127.0.0.1:8181"
  auth:
    jwt_secret: "${JWT_SECRET}"
    users:
      - username: admin
        password_hash: "${GODHCP_ADMIN_HASH}"
        role: admin
web:
  enabled: true
  path: /ui
vlans:
  - id: 50
    name: lab
    interface: eth0
    subnet_ref: lab
subnets:
  - id: lab
    network: 192.168.50.0/24
    range: [192.168.50.100, 192.168.50.150]
    gateway: 192.168.50.1
    dns: [192.168.50.1]
    vlan: 50
relay:
  enabled: false
metrics:
  enabled: true
  listen: "127.0.0.1:9090"
logging:
  level: info
  format: json
```

Создайте отдельный секрет JWT и хэш пароля. Команда хэширования принимает пароль аргументом процесса; выполняйте её на доверенной административной машине. Ввод через `read` исключает пароль из истории команд оболочки.

```bash
umask 077
read -r -s -p 'Пароль администратора: ' admin_password
printf '\n'
admin_hash=$(/usr/bin/godhcp hash-password -password "$admin_password")
unset admin_password
test -n "$admin_hash" || exit 1
printf 'JWT_SECRET=%s\n' "$(openssl rand -hex 32)" > /etc/godhcp/godhcp.env
printf "GODHCP_ADMIN_HASH='%s'\n" "$admin_hash" >> /etc/godhcp/godhcp.env
unset admin_hash
chown root:godhcp /etc/godhcp/godhcp.env
chmod 0640 /etc/godhcp/godhcp.env
chown godhcp:godhcp /etc/godhcp/config.yml
chmod 0640 /etc/godhcp/config.yml
set -a
. /etc/godhcp/godhcp.env
set +a
/usr/bin/godhcp -validate -config /etc/godhcp/config.yml
```

Одинарные кавычки вокруг хэша в env-файле сохраняют символы `$` при чтении оболочкой. Файл подходит также для `EnvironmentFile` systemd. Все переменные `${...}` должны быть доступны при валидации и запуске.

Для trunk создайте VLAN-интерфейсы средствами ОС и настройте постоянное восстановление после перезагрузки; сопоставьте их с `vlans` и `subnets`. Для relay включите `relay.enabled`, укажите доверенные агенты и маршрутизацию подсетей по [руководству relay](relay.md). Параметры интерфейсов и firewall подбираются под реальную сеть.

## Запуск через systemd

При пакетной установке unit уже находится в `/usr/lib/systemd/system/godhcp.service`; проверьте его через `systemctl cat godhcp`. При ручной установке используйте `deploy/systemd/godhcp.service` из исходников или `godhcp.service` из архива, либо создайте `/etc/systemd/system/godhcp.service` со следующим содержимым:

```ini
[Unit]
Description=GoDHCP IPv4 server
Wants=network-online.target
After=network-online.target

[Service]
Type=notify
NotifyAccess=main
RuntimeDirectory=godhcp
RuntimeDirectoryMode=0700
User=godhcp
Group=godhcp
WorkingDirectory=/var/lib/godhcp
EnvironmentFile=/etc/godhcp/godhcp.env
ExecStartPre=/usr/bin/godhcp -validate -config /etc/godhcp/config.yml
ExecStart=/usr/bin/godhcp -config /etc/godhcp/config.yml -control-socket /run/godhcp/control.sock
ExecReload=/usr/bin/godhcp reload -socket /run/godhcp/control.sock
TimeoutStartSec=30
TimeoutStopSec=15
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
UMask=0027
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Этот unit рассчитан на SQLite, отключённый ping-check и интерфейсы, созданные ОС. Он запускает процесс от `godhcp` и даёт только `CAP_NET_BIND_SERVICE` для открытия порта 67. В `systemctl show godhcp` проверьте `Type=notify`, `User=godhcp`, `NoNewPrivileges=yes` и набор capabilities. Секреты в env-файле остаются root:root 0600; systemd читает его до смены пользователя. SQLite и YAML должны быть доступны пользователю godhcp; остальным пользователям чтение секретов и БД не требуется. Для управления VLAN через API понадобятся дополнительные права и отдельно проверенная настройка `CAP_NET_ADMIN`.

Убедитесь, что в стендовом сегменте нет другого DHCP-сервера, затем:

```bash
systemctl daemon-reload
systemctl start godhcp
systemctl status godhcp --no-pager
journalctl -u godhcp -n 100 --no-pager
ss -lunp 'sport = :67'
curl --fail http://127.0.0.1:8181/healthz
curl --fail http://127.0.0.1:8181/readyz
```

Проверьте в `ss`, что порт принадлежит именно GoDHCP. Сообщение `dhcp listening` и HTTP 200 сами по себе не подтверждают работу DHCP. После успешной приёмки включите автозапуск: `systemctl enable godhcp`.

## Работа с веб-интерфейсом

Откройте `http://127.0.0.1:8181/ui/`, войдите как `admin` с выбранным паролем. Интерфейс на Tailwind CSS встроен в бинарник, включая стили и иконки; подключение к CDN не требуется. По умолчанию сеанс хранится до закрытия вкладки; «Запомнить вход» сохраняет его на устройстве. Сменить светлую/тёмную тему можно кнопкой в верхней панели.

- **Обзор** показывает занятость пулов, подсети, VLAN, время работы и выборку аренд. Зелёный индикатор «API доступен» означает доступность управления, а не проверку сетевого DHCP-порта.
- **Аренды**: поиск по IP, MAC и имени, фильтры VLAN/состояния, размер страницы и переход между страницами. Кнопка CSV экспортирует текущую выборку страницы. Удаление требует подтверждения; устройство может использовать IP до конца аренды, даже если запись удалена.
- **Подсети, резервации, VLAN, relay**: таблицы и раскрывающиеся формы добавления. При создании резервации укажите MAC либо Client ID в hex-формате, IP и подсеть. Для Circuit ID доступен тест парсера без изменения настроек.
- **Конфигурация**: YAML-редактор, проверка перед применением, подтверждение сохранения, экспорт и перечитывание файла. Экспорт скрывает JWT и API-ключи и не заменяет резервную копию секретов. Не применяйте YAML из недоверенных источников.
- **Журнал**: поток SSE, поиск, пауза, автоматическая прокрутка и очистка экрана. В браузере удерживается до 1000 событий; очистка экрана не удаляет серверные журналы.
- **Пользователи**: роли admin/operator/viewer. Кнопки и разделы показываются с учётом роли; доступ дополнительно проверяется сервером. UI блокирует удаление последнего администратора, но при прямом редактировании конфигурации всё равно проверяйте, что учётные данные остались.

На телефоне навигация открывается кнопкой меню. Широкие таблицы прокручиваются горизонтально. Кнопка обновления в верхней панели перечитывает данные текущего раздела.

Для удалённого управления используйте SSH-туннель с рабочей станции:

```bash
ssh -L 18080:127.0.0.1:8181 admin@dhcp-host
```

После этого откройте `http://127.0.0.1:18080/ui/`. API и метрики в примере доступны только через loopback; при публикации на другом адресе настройте TLS и сетевые ограничения.

## Приёмка и переключение с ISC DHCP

1. Используйте исправленную версию 0.1.3 или новее и выполните тестирование с учётом оставшихся ограничений. Подготовьте резервные копии и окно работ, подтвердите способ удалённого доступа при отказе DHCP.
2. Сверьте исходный ISC-конфиг и YAML: подсети, диапазоны, резервации, сроки, DHCP options, PXE и relay. Для каждой активной аренды определите, как её IP будет исключён из повторной выдачи.
3. Проверьте на стенде полный обмен DISCOVER → OFFER → REQUEST → ACK, продление, резервации, исчерпание пула, каждый VLAN и каждый relay. Выполните перезапуск с сохранённой базой и убедитесь, что выданные адреса остаются занятыми.
4. В окно переключения остановите ISC DHCP на всех узлах, способных отвечать в переносимом сегменте, включая failover-партнёра. Сохраните финальный снимок аренд. При переносе на другой хост измените DHCP relay / IP helper на сетевом оборудовании по согласованной схеме.
5. Запустите GoDHCP с подготовленной базой и безопасным пулом. Проверьте порт, журнал и реальную выдачу тестовому клиенту в каждом сегменте. Сверьте IP, маску, шлюз, DNS, server-id и время аренды.
6. Наблюдайте за продлениями старых клиентов и отсутствием конфликтов IP. Включайте автозапуск нового сервера после приёмки.

Не запускайте ISC DHCP и GoDHCP одновременно в одном сегменте с пересекающимися пулами. Для диагностики обмена используйте:

```bash
tcpdump -ni eth0 -vvv 'udp port 67 or udp port 68'
```

При необходимости замените `eth0` на VLAN-интерфейс; захват может содержать идентификаторы клиентов.

### Откат

Сначала остановите GoDHCP: `systemctl stop godhcp`. Верните настройки relay и прежний сервис ISC DHCP, используя сохранённый конфиг. До запуска ISC учтите адреса, уже выданные GoDHCP: старая база ISC о них не знает. При непересекающихся пулах оставьте новый диапазон исключённым; при пересечении потребуется согласование занятости. Простое восстановление старого файла аренд не обеспечивает безопасный откат после новых выдач.

После проверки пула запустите прежнюю службу (`systemctl start isc-dhcp-server` либо `dhcpd`) и подтвердите выдачу клиенту. Сохраните базу и журнал GoDHCP для разбора причины отката.

## Изменение настроек

Перед изменением сохраните рабочий YAML и секреты. Проверяйте конфиг с теми же переменными окружения, что использует служба:

```bash
set -a
. /etc/godhcp/godhcp.env
set +a
/usr/bin/godhcp -validate -config /etc/godhcp/config.yml
systemctl reload godhcp
journalctl -u godhcp -n 50 --no-pager
```

Reload обновляет подсети, пулы и часть логики в памяти; UDP/HTTP-слушатели, подключение БД и настройки логирования не пересоздаются. Для изменения listen, TLS, базы, env-файла или журналирования нужен перезапуск. В unit версии 0.1.3 `systemctl reload` вызывает `godhcp reload` через `/run/godhcp/control.sock` и ожидает результата применения в работающем процессе. При ошибке YAML или применения команда завершается ненулевым кодом; для ошибок проверки YAML прежняя конфигурация остаётся активной. Прямой SIGHUP по-прежнему поддерживается, но не сообщает вызывающему процессу результат. Управляющий сокет имеет права 0600 в каталоге 0700, принадлежащем службе; его создаёт и удаляет systemd через RuntimeDirectory.

В Docker/Kubernetes ConfigMap и mount `:ro` нельзя сохранять из UI. Текущий API сначала применяет конфиг в памяти и только затем пишет файл; ошибка записи может оставить новое состояние активным. При таком развёртывании меняйте конфиг снаружи и перезапускайте экземпляр. Helm-шаблоны сейчас используют `emptyDir` для SQLite: замените его постоянным томом до эксплуатации, иначе пересоздание Pod потеряет аренды.

## Резервное копирование и восстановление

Сохраняйте вместе бинарный файл или его точную версию, `/etc/godhcp/config.yml`, `/etc/godhcp/godhcp.env` и базу аренд. Экспорт `/api/v1/config` маскирует JWT и API-ключи; для полной копии нужен исходный файл и все внешние секреты.

Для SQLite установите утилиту `sqlite3`. Онлайн-копию создавайте через `.backup`, чтобы учесть WAL; обычный `cp leases.db` во время работы не гарантирует полноту. См. [CLI SQLite](https://www.sqlite.org/cli.html) и [описание online backup](https://www.sqlite.org/backup.html).

```bash
umask 077
backup_dir="/root/godhcp-backup-$(date +%Y%m%d-%H%M%S)"
install -d -m 0700 "$backup_dir"
cp -a /etc/godhcp/config.yml /etc/godhcp/godhcp.env "$backup_dir/"
sqlite3 /var/lib/godhcp/leases.db ".backup '$backup_dir/leases.db'"
sqlite3 "$backup_dir/leases.db" 'PRAGMA integrity_check;'
```

Ожидаемый результат `integrity_check` — `ok`. На время получения согласованного комплекта запретите изменения конфигурации; для точного снимка на один момент остановите службу перед копированием. Перенесите резервную копию на отдельный носитель с ограниченным доступом.

При восстановлении остановите службу, сохраните весь текущий каталог БД вместе с `-wal` и `-shm`, затем установите проверенную копию в чистый каталог. Не подмешивайте старые WAL-файлы к восстановленной БД. Восстановите YAML, env-файл и владельца `godhcp:godhcp`, проверьте конфиг и права, запустите службу. Учитывайте аренды, выданные после снимка: восстановление старой БД не делает эти IP свободными.

## Повторяемый сетевой стенд в Docker

Из корня исходного проекта на машине с Go и работающим Docker выполните:

```bash
make test-dhcp-docker
```

Скрипт собирает Linux-бинарник под архитектуру Docker daemon и образ Debian 12 с независимым Scapy-клиентом, ISC dhclient и ISC dhcrelay. Требуются Docker с поддержкой privileged-контейнеров, network namespace и 802.1Q; при сборке образа нужен доступ к Debian-репозиториям. Docker Desktop на ARM64 проверен; на amd64 скрипт выбирает amd64-сборку, но отдельный сетевой прогон на amd64 пока не выполнен.

Стенд работает с `--network none`: veth, namespace, VLAN 20/30 и relay создаются внутри одноразового контейнера. UDP 67/68 не публикуются, рабочие интерфейсы хоста не подключаются. Privileged нужен для этих внутренних сетевых операций. Не запускайте Python-сценарий напрямую на рабочем Linux-хосте.

Проверяются DORA с broadcast-флагом и без него, unicast-продление с увеличением срока в БД, автоматическое продление ISC dhclient по T1, выбор пула и изоляция VLAN, явное имя VLAN-интерфейса, ISC relay и точное эхо Option 82, корректный NAK, игнорирование BOOTREPLY, сохранение RELEASE с повторным получением аренды и карантин адреса после DECLINE с выдачей другого IP. После перезапуска процесса сверяется БД и отсутствие повторной выдачи занятого адреса. Затем первый контейнер удаляется, создаётся новый с прежним каталогом SQLite и проверяется продление старого клиента и выдача новому.

Результаты, конфиг, SQLite, журналы и захваты пакетов сохраняются в `output/dhcp-lab/`: `report.json` содержит 20 проверок, `recreated-report.json` - проверку нового контейнера. `vlan-wire.pcap` подтверждает реальные теги 802.1Q и PCP 6/5, `relay-wire.pcap` - обмен с relay и Option 82; отдельные PCAP показывают обмены клиентов. При сбое команда завершается ненулевым кодом. Повторный запуск очищает только тестовую БД и состояние dhclient в этом каталоге. Стенд не проверяет systemd как PID 1, PostgreSQL и физические коммутаторы.

## Проверка systemd с настоящей перезагрузкой Linux

Для проверки собранных пакетов из исходного проекта выполните:

```bash
bash scripts/test-systemd-vm.sh
```

Сначала должны существовать пакеты текущей версии в `dist/releases/<version>/`. Нужны Go для их сборки, Docker, Python 3 на машине запуска и интернет при подготовке образов. Скрипт использует QEMU ARM64 с программной эмуляцией, поэтому запускается и на amd64 без KVM. Диску Docker потребуется несколько гигабайт, проверка длится несколько минут. Для одного дистрибутива передайте `debian` или `rocky`.

Стенд создаёт отдельные полноценные виртуальные машины из минимальных Debian 12 и Rocky Linux 9 с их собственными пакетами ядра и systemd PID 1. Виртуальных внешних сетевых карт нет; DHCP-клиент подключён внутренним veth. После первой серии проверок внутри гостя выполняется `systemctl reboot`: смена kernel boot_id подтверждает настоящую перезагрузку ядра, затем systemd автоматически запускает включённую службу. Это не замена перезагрузки рестартом процесса или контейнера.

На каждом дистрибутиве проверяются пользователь godhcp, единственная capability для UDP 67, NoNewPrivileges, права env/SQLite/YAML, DORA через пакетный unit, изменение DNS через reload без смены PID, отказ reload при неправильном YAML, ошибка запуска при занятом UDP 67, сохранение аренд при рестарте службы, автозапуск после перезагрузки и продление прежней аренды без повторной выдачи занятого адреса. Для старта, reload и управления службой используйте root или разрешённый sudo; сетевой процесс root не требует.

Отчёты находятся в `output/systemd-lab/debian/godhcp-lab/report.json` и `output/systemd-lab/rocky/godhcp-lab/report.json`; рядом сохранены журналы обоих запусков, свойства unit, kernel boot_id и PCAP. Ненулевой код означает сбой проверки. Образы стенда минимальные: SELinux enforcing, firewalld, реальные NIC и загрузка физического сервера отдельно не моделируются.

## Запись журналов в файл и logrotate

По умолчанию GoDHCP пишет в stdout; при запуске пакетной службы systemd это попадает в journald. Просмотр:

```bash
sudo journalctl -u godhcp -f -o cat
```

Для дополнительной записи в файл создайте каталог с правом записи для пользователя службы. Пакетный unit запускает процесс от `godhcp`; если у вас другой пользователь, замените его и в командах, и в правиле ротации.

```bash
sudo install -d -m 0750 -o godhcp -g godhcp /var/log/godhcp
```

В существующем YAML укажите:

```yaml
logging:
  level: info
  format: json
  output: /var/log/godhcp/godhcp.log
```

`output: "-"` или отсутствие `output` оставляет только stdout. `format` принимает `json` или `text`; уровни - `debug`, `info`, `warn`, `error`. При выборе файла stdout сохраняется, поэтому записи продолжают поступать в journald и в журнал веб-интерфейса. Файл открывается с append, создаётся с правами 0640; существующие права не изменяются автоматически. Веб-журнал - буфер последних событий в памяти, а не замена файловому архиву.

После изменения `logging` нужен **restart**, а не reload. Каталог программа автоматически не создаёт. Если файл открыть не удалось, текущий код продолжает писать только в stdout, поэтому обязательно проверьте фактическое появление файла:

```bash
sudo systemctl restart godhcp
sudo ls -l /var/log/godhcp/godhcp.log
sudo tail -n 30 /var/log/godhcp/godhcp.log
```

Не перенаправляйте одновременно stdout службы через `StandardOutput=append:` в тот же файл: GoDHCP уже пишет в оба канала и записи могут дублироваться.

### Настройка ротации

Установите logrotate средствами своего дистрибутива: Debian, Astra и ALT Linux - `apt-get install logrotate`; Rocky Linux и РЕД ОС - `dnf install logrotate`. Готовый пример включён в пакет и архив: `docs/examples/godhcp.logrotate`. При пакетной установке включите его:

```bash
sudo install -o root -g root -m 0644 \
  /usr/share/doc/godhcp/examples/godhcp.logrotate \
  /etc/logrotate.d/godhcp
```

При ручной установке скопируйте пример из распакованного каталога docs. Содержимое `/etc/logrotate.d/godhcp`:

```text
/var/log/godhcp/godhcp.log {
    daily
    maxsize 100M
    rotate 14
    missingok
    notifempty
    compress
    delaycompress
    nodateext
    copytruncate
    su godhcp godhcp
}
```

Правило хранит до 14 архивов, пропускает отсутствующий или пустой файл, сжимает архивы с задержкой в одну ротацию. Используются имена `godhcp.log.1`, `godhcp.log.2.gz` и далее; `nodateext` позволяет выполнять несколько ротаций за сутки без конфликта имени. `daily` задаёт суточную ротацию; `maxsize 100M` разрешает более раннюю при очередном запуске logrotate, если размер превышен. Это не жёсткий лимит: между проверками файл может вырасти больше 100 MiB.

В этой версии лог-файл не переоткрывается ни через SIGHUP, ни через `systemctl reload`. Поэтому обычная схема rename/create с `postrotate kill -HUP` не подходит: запись продолжится в старый файл. `copytruncate` сохраняет открытый файл и позволяет ротировать без перезапуска DHCP. Между копированием и усечением есть небольшое окно возможной потери строк в файловом архиве; не считайте этот способ гарантией без потерь. Параллельный stdout остаётся доступен через journald с его собственной политикой хранения и ограничения частоты. Это поведение описано в [руководстве logrotate](https://man7.org/linux/man-pages/man8/logrotate.8.html).

### Проверка и автоматический запуск

Сначала проверьте синтаксис без изменения файлов; затем при необходимости выполните одну принудительную ротацию:

```bash
sudo logrotate -d /etc/logrotate.d/godhcp
sudo logrotate -v -f /etc/logrotate.d/godhcp
sudo ls -l /var/log/godhcp/
sudo tail -f /var/log/godhcp/godhcp.log
```

После ротации новые события должны появляться в текущем `godhcp.log`, владелец должен оставаться `godhcp`, служба должна оставаться active, её PID не должен меняться. Используйте эту проверку в стендовом сегменте и учитывайте описанное окно copytruncate.

У logrotate должен быть автоматический планировщик. Если дистрибутив предоставляет `logrotate.timer`, включите и проверьте его:

```bash
sudo systemctl enable --now logrotate.timer
systemctl list-timers --all logrotate.timer
systemctl cat logrotate.timer
```

Если timer отсутствует, проверьте дистрибутивный cron, например `/etc/cron.daily/logrotate`, и работу службы cron; второй независимый планировщик не добавляйте. Для интенсивных логов суточной проверки размера может быть мало. При использовании systemd можно изменить существующий timer через `sudo systemctl edit logrotate.timer`:

```ini
[Timer]
OnCalendar=
OnCalendar=hourly
AccuracySec=1m
Persistent=true
```

Затем выполните `sudo systemctl daemon-reload` и `sudo systemctl restart logrotate.timer`. Это повышает частоту проверки **всех** правил этого timer, а не только GoDHCP; суточные условия остальных правил продолжают учитываться. Проверяйте свободное место и фактическое число архивов.

## Ежедневная проверка и диагностика

- Служба активна, UDP 67 принадлежит GoDHCP, в журнале нет `dhcp send`, `persist lease`, `pool allocate failed`, ошибок БД и bind. При `persist lease` проверьте доступность БД, место на диске и права: OFFER/ACK для незафиксированной аренды теперь не отправляется. Когда чтение работает, пул восстанавливается из БД; если недоступны и чтение, и запись, занятость сохраняется консервативно до сверки. После восстановления БД выполните проверку и reload, чтобы убрать временно удержанные адреса.
- На UI проверьте пулы и аренды; значение занятости включает резервации и удержанные адреса и не равно числу подключённых устройств.
- Метрики доступны на `http://127.0.0.1:9090/metrics`. Следите за исчерпанием пулов, отклонёнными relay и ошибками разбора.
- Если нет OFFER, проверьте firewall, интерфейс/VLAN, наличие подсети и доступность UDP 67. Если нет ACK, сверяйте запрошенный адрес, server-id и состояние аренды.
- Для relay проверьте `giaddr`, маршруты в обе стороны, trusted relay, Option 82, hops и формат Circuit ID. Не включайте `default-pool` для неизвестных VLAN без явной необходимости.
- Удаление пользователя пока не отзывает выданные JWT; refresh-токен сохраняет прежнюю роль. При срочном отзыве доступа смените JWT secret и перезапустите службу; это завершит все JWT-сеансы. API-ключи отзываются удалением из конфигурации.

Дополнительно: [параметры YAML](configuration.md), [REST API](api.md), [VLAN](vlans.md), [relay](relay.md), [формат импорта](import-dhcpd.md).

## LDAP, роли и делегирование VLAN


### Настройка через веб

Войдите локальным глобальным администратором и откройте **Пользователи**.

1. В блоке **Группы доступа** создайте группу, выберите роль и область «Выбранные VLAN», отметьте нужные VLAN. Поле LDAP DN оставьте пустым для локальной группы либо укажите полный DN группы AD/FreeIPA.
2. Создайте локального пользователя или нажмите «Изменить» у существующего. Можно назначить прямую роль для выбранных VLAN или выбрать «Только права групп» и отметить группы доступа. При изменении пустой пароль сохраняет текущий пароль; новый пароль — минимум 8 символов.
3. Для полного управления выберите роль «Администратор» и область **Весь сервер**. Сохраняйте хотя бы одного локального глобального администратора для аварийного входа.
4. В блоке **LDAP** задайте адрес, Base DN, Bind DN и пароль служебной учётной записи. Шаблон «Microsoft Active Directory» подставляет фильтр `(&(objectClass=user)(sAMAccountName={username}))`, FreeIPA — `(&(objectClass=person)(uid={username}))`. Вход выполняется коротким именем, используемым выбранным фильтром.
5. Используйте `ldaps://dc.example.org:636` либо `ldap://dc.example.org:389` с включённым StartTLS. Для внутреннего центра сертификации укажите абсолютный путь к PEM-файлу CA на сервере, например `/etc/godhcp/ldap-ca.pem`; файл должен читаться пользователем службы. Имя сервера должно совпадать с сертификатом. Проверка сертификатов обязательна.
6. Отметьте «Включить вход через LDAP», введите существующего пользователя для проверки и нажмите «Проверить соединение и поиск». Это проверяет TLS, служебный bind и уникальность результата поиска; пароль самого пользователя проверяется при настоящем входе. Затем сохраните LDAP.
7. Сопоставьте группы с DN из результата проверки. Войдите в отдельном окне браузера тестовым пользователем и проверьте доступ к назначенным VLAN.

Сохранение через веб обновляет активную конфигурацию и YAML-файл, указанный при запуске; перезапуск не нужен. Для постоянного сохранения службе нужны права на каталог конфигурации. Если файл не удалось сохранить, API возвращает ошибку и восстанавливает предыдущую активную конфигурацию. При запуске без пути конфигурации изменения существуют только в памяти. Пароль служебного LDAP-пользователя хранится в конфигурации и скрывается как `***` в веб-ответах и экспорте. При сохранении `***` прежнее значение сохраняется.

### Роли и ограничения

- **Администратор**: в глобальной области — настройки сервера, пользователи, группы, LDAP, парсеры и все сетевые объекты; в области VLAN — свои VLAN, подсети, аренды и резервации.
- **Оператор**: аренды, резервации и диагностика в назначенной области.
- **Наблюдатель**: чтение в назначенной области.

Права групп складываются отдельно для каждого VLAN: администратор VLAN 10 и наблюдатель VLAN 20 не получает права изменения VLAN 20. Прямая роль пользователя также добавляется к групповым правам; для доступа исключительно через группы выберите «Только права групп».

Пустой список `vlan_ids` у роли или группы означает глобальную область. Выбор «Выбранные VLAN» в веб требует хотя бы одного VLAN. Разрешения можно подготовить для VLAN, который ещё не создан, через YAML; веб показывает настроенные VLAN.

Сервер проверяет доступ к отдельным объектам и фильтрует списки, счётчики и аренды до SQL-пагинации. Изолированный администратор VLAN не получает общий YAML, настройки доступа, журналы всего сервера, общие метрики или управление доверенными relay и парсерами. Интерфейсы Linux, PCP и правила сопоставления пакетов в VLAN настраивает глобальный администратор. Для общей подсети, связанной с несколькими VLAN, требуются права на все связанные VLAN; подсеть без принадлежности к VLAN доступна глобальным ролям.

При удалении локального пользователя старые access/refresh JWT перестают приниматься на следующий запрос. Назначения ролей и групп проверяются по текущей конфигурации, включая старые access JWT. При смене пароля уже выданные JWT сохраняются до истечения срока; для немедленного отзыва всех сеансов смените `jwt_secret`.

LDAP работает через служебный поиск пользователя и bind найденного DN с введённым паролем. Пустой пароль отвергается. Группы берутся из `memberOf` (или другого настроенного атрибута), сравниваются по DN без учёта регистра. Вложенные группы и primaryGroup AD автоматически не раскрываются. Назначайте прямое членство в группах доступа. Пользователь без сопоставленных прав не допускается. Локальное имя имеет приоритет: ошибочный локальный пароль не приводит к попытке LDAP с тем же именем.

Членство LDAP-групп обновляется при входе и refresh; между ними действует подписанный снимок членства до окончания access JWT (`token_ttl`, по умолчанию 1 час). Изменения локальных сопоставлений LDAP-групп действуют на следующий запрос. При недоступном каталоге новые LDAP-входы и refresh отклоняются, локальный вход продолжает работать. Это LDAP-аутентификация по паролю, не Kerberos/SSO.

### Пример YAML

```yaml
api:
  auth:
    jwt_secret: "${JWT_SECRET}"
    token_ttl: 15m
    refresh_ttl: 24h
    ldap:
      enabled: true
      url: ldaps://dc.example.org:636
      start_tls: false
      ca_file: /etc/godhcp/ldap-ca.pem
      bind_dn: CN=svc-dhcp,OU=Service,DC=example,DC=org
      bind_password: "${LDAP_BIND_PASSWORD}"
      base_dn: DC=example,DC=org
      user_filter: '(&(objectClass=user)(sAMAccountName={username}))'
      group_attribute: memberOf
      timeout_seconds: 5
    groups:
      - name: dhcp-vlan120-admins
        role: admin
        vlan_ids: [120]
        ldap_dn: CN=DHCP-VLAN120,OU=Groups,DC=example,DC=org
    users:
      - username: emergency-admin
        password_hash: "<argon2id hash from godhcp hash-password>"
        role: admin
      - username: local-operator
        password_hash: "<argon2id hash>"
        role: ""
        groups: [dhcp-vlan120-admins]
```

Это фрагмент, который нужно объединить со своей конфигурацией. Редактирование через веб сохраняет уже раскрытые значения переменных окружения в YAML; ограничьте права файла. Ключи API также поддерживают `vlan_ids`, настройка ключей выполняется через глобальный YAML.

Проверки реализации: автоматические тесты TLS LDAP (LDAPS и StartTLS), проверка CA, служебный и пользовательский bind, неверный/пустой пароль, неоднозначный поиск, экранирование LDAP-фильтра; тесты API для изоляции VLAN, смешанных групп, отзыва прав и скрытия секретов. Совместимость с конкретным сервером AD/FreeIPA проверяется на вашей схеме каталога; подключение к рабочему каталогу в ходе разработки не выполнялось.


## Отечественные relay и парсеры


В **Relay-агенты → Парсеры отечественного оборудования** доступны Eltex, QTECH, UserGate, Код Безопасности / Континент, SNR, NATEKS и произвольный производитель. Выбор производителя не меняет сетевую конфигурацию и не создаёт VLAN.

Встроенное распознавание включает:

- `eltex`: текстовый TR-101 Circuit ID `eth 1/8:120` или `esr01 eth 1/0/1:120` с VLAN 120. Бинарные варианты требуют отдельной поддержки; это не универсальный формат всех устройств Eltex.
- `qtech`: `vlan120+Ethernet1/0/8` с VLAN 120 для серий и конфигураций с таким ASCII-форматом.

Предустановка **Eltex · slot/port:vlan** даёт шаблон для настроенного формата spv с разделителями `/` и `:` — `1/8:120`. Она становится активной после сохранения. Форматы sp без номера VLAN не позволяют определить VLAN из Circuit ID.

Для UserGate, «Континента», SNR и NATEKS предусмотрены именованные пользовательские профили. Универсальное автоматическое определение VLAN для этих брендов не заявляется: нужен реальный образец Option 82 и шаблон для конкретной модели/прошивки. Если relay не передаёт Circuit ID, сопоставляйте подсеть по `giaddr` через доверенный relay. В UserGate поле адреса relay влияет на `giaddr`.

Порядок настройки:

1. Выберите производителя и формат. Для своего шаблона задайте регулярное выражение Go RE2 с именованной группой `(?P<vlan>...)`.
2. Скопируйте реальный текст Circuit ID из журнала или захвата DHCP. При необходимости проверьте Option 82 в Wireshark; бинарный hex-дамп не является текстовым форматом из примеров.
3. Нажмите **Проверить шаблон**. Эта проверка не меняет настройки. Принимаются VLAN от 1 до 4094.
4. Проверьте также соседние порты, VLAN и строки, которые не должны совпадать. Избегайте слишком общих шаблонов, извлекающих номер порта как VLAN.
5. Сохраните парсер. Он сохраняется в `relay.circuit_id_parsers` и участвует в автоматическом определении. Совпадающее имя заменяет предыдущий шаблон, включая встроенный.
6. Для изменения используйте «Изменить» в списке сохранённых парсеров. Удаление пользовательского переопределения встроенного имени восстанавливает встроенный шаблон.

В проверке Circuit ID явный выбор парсера проверяет только его. «Автоматическое определение» перебирает эффективный список по порядку. Неоднозначные текстовые форматы разных производителей могут совпадать; имя сработавшего парсера само по себе не подтверждает производителя.

Источники форматов: [Eltex ESR — настройка DHCP и форматов Option 82](https://docs.eltex-co.ru/pages/viewpage.action?pageId=55183793), [QTECH — форматы DHCP relay](https://www.qtech.ru/support/wiki/113/11253/), [UserGate — настройка DHCP relay](https://docs.usergate.com/nastrojka-dhcp-relay-i-osobennosti-raboty_643.html).
