# Обновление DNS Samba AD из GoDHCP

© 2026 Кислов Роман Сергеевич. Apache License 2.0.

Функция доступна начиная с версии 0.1.10. Бинарники 0.1.9 её не содержат. По умолчанию DDNS выключен. Само размещение GoDHCP на контроллере домена не включает обновления автоматически.

## Как это работает

После сохранения подтверждённой аренды фоновый обработчик создаёт A-запись имени клиента и PTR-запись адреса. Продление обновляет записи; переименование, освобождение, удаление и истечение аренды приводят к очистке прежних записей. DHCP-ответ не ждёт DNS: сбои записываются в журнал, операции повторяются. Периодическая сверка по умолчанию выполняется через 30 секунд; подтверждение аренды также будит обработчик, объединяющий события в течение секунды. При большом числе аренд синхронизация может занимать несколько циклов.

Обновления выполняются через `nsupdate -g` с Kerberos/GSS-TSIG. У каждой управляемой записи есть TXT-метка `_godhcp-owner.<имя>`. DNS-предусловия проверяют владение атомарно с изменением. Существующие A/PTR без метки GoDHCP, а также записи другого экземпляра не перезаписываются. При конфликте A новая PTR для этого имени также не создаётся. Несколько активных клиентов с одинаковым именем блокируют обновления этого имени до устранения конфликта.

Некоторые версии Samba Internal DNS применяют изменение, но возвращают ответ, который `nsupdate` не может проверить (`tsig verify failure`). При `samba_verify: true` GoDHCP независимо подтверждает результат через `samba-tool dns query` с обязательным Kerberos, отдельным кешем билетов и подписанным RPC. Для записи должны совпасть метка владения, значение и TTL; неподтверждённый результат остаётся на повтор. Отключения проверки подлинности и перехода на анонимное обновление нет.

## Подготовка контроллера домена

Примеры используют `dc01.example.org`, realm `EXAMPLE.ORG`, прямую зону `hosts.example.org` и сеть `192.0.2.0/24`. Замените их своими значениями. Это не настройки VLAN112.

На Debian необходимые клиентские программы устанавливаются так:

```bash
apt-get install krb5-user bind9-dnsutils samba-common-bin
```

На других дистрибутивах установите пакеты, содержащие `kinit`, `nsupdate` и `samba-tool`. Они должны быть в PATH службы. DNS контроллера должен разрешаться по FQDN, время сервера и KDC — быть синхронизировано, `/etc/krb5.conf` — описывать действующий realm. Для GSS-TSIG используйте настоящее DNS-имя контроллера, соответствующее его Kerberos SPN, а не IP или произвольный псевдоним.

На контроллере создайте отдельную служебную учётную запись. Команда создания интерактивно запросит пароль:

```bash
samba-tool user create dhcp-dns
samba-tool group addmembers DnsAdmins dhcp-dns
samba-tool domain exportkeytab /root/dhcp-dns.keytab --principal=dhcp-dns
install -o root -g godhcp -m 0640 /root/dhcp-dns.keytab /etc/godhcp/dhcp-dns.keytab
rm /root/dhcp-dns.keytab
```

`DnsAdmins` даёт широкие права управления DNS домена. Для ограниченной схемы делегируйте служебной записи права только на нужные зоны средствами AD и проверьте создание, изменение и удаление A/PTR/TXT. Стендовые тесты используют `DnsAdmins`; конкретные ACL делегации не проверялись. Не выдавайте процессу GoDHCP доступ к `sam.ldb`, приватным файлам Samba или keytab машинной учётной записи DC.

Учитывайте политику срока действия пароля служебной записи. После его смены экспортируйте и установите новый keytab. Не помещайте keytab в Git, общедоступные каталоги или выгрузки конфигурации. LDAP-вход пользователей и DDNS используют независимые учётные данные.

Прямая и обратная зоны должны существовать заранее. Если используете отдельную новую зону, создайте её с правами администратора домена:

```bash
samba-tool dns zonecreate dc01.example.org hosts.example.org -U Administrator
samba-tool dns zonecreate dc01.example.org 2.0.192.in-addr.arpa -U Administrator
```

Не повторяйте создание существующих зон. Для общей зоны домена отдельно внесите имена DC, шлюзов и инфраструктурных серверов в `protected_names`.

## Настройка через веб

Войдите глобальным администратором. Откройте **Конфигурация → Динамический DNS · Samba AD**. Укажите сервер, прямую и обратные зоны, principal и путь к keytab. Включите A/PTR и проверку RPC Samba, затем включите DDNS и нажмите **Сохранить DDNS**. Настройки сохраняются в конфигурационный файл и применяются без перезапуска. Если YAML-редактор содержит несохранённые изменения, сначала примените или отмените их.

Путь к keytab относится к серверу, на котором запущен демон. Веб-форма не загружает ключ и не создаёт пользователя или DNS-зоны. Администраторы отдельных VLAN не имеют доступа к глобальным настройкам DDNS.

Эквивалентный блок конфигурации:

```yaml
ddns:
  enabled: true
  auth: gss-tsig
  server: dc01.example.org
  port: 53
  zone: hosts.example.org
  reverse_zones:
    - 2.0.192.in-addr.arpa
  principal: dhcp-dns@EXAMPLE.ORG
  keytab: /etc/godhcp/dhcp-dns.keytab
  samba_verify: true
  hostname: true
  update_a: true
  update_ptr: true
  protected_names: [dc01, dc02, gateway]
  ttl: 300
  interval_seconds: 30
  timeout_seconds: 10
```

`reverse_zone` поддерживается для совместимости; для нескольких сетей используйте `reverse_zones`. Обратные зоны IPv4 поддерживаются на границах /8, /16 и /24; выбирается наиболее специфичная подходящая зона. RFC2317/classless reverse delegation и IPv6 не реализованы. При отсутствии подходящей обратной зоны PTR адреса не создаётся. `auth: tsig` с абсолютным `key_file` предусмотрен для DNS-сервера BIND с соответствующей политикой ключа, а не как замена Kerberos для Samba Internal DNS.

`hostname: true` разрешает имена клиентов; `false` ограничивает обновления именами настроенных резерваций. Короткое имя дополняется прямой зоной. Полное имя принимается только внутри этой зоны. Имена должны состоять из допустимых ASCII DNS-меток; IDN передавайте в punycode. Имена `wpad`, `isatap`, `autodiscover`, имя выбранного DNS-сервера и `protected_names` не регистрируются.

DHCP Option81 имеет приоритет над Host Name (Option12). Запрос клиента N=1 запрещает обновления и приводит к удалению ранее управляемых записей. Продление без обоих полей сохраняет прежнее имя того же клиента. Если доменные Windows-клиенты сами регистрируют A, можно выбрать `update_a: false`, `update_ptr: true`; GoDHCP будет управлять только PTR. По умолчанию имеющиеся записи, созданные клиентами или старым ISC DHCP, не принимаются под управление. Для их обновления явно включите `adopt_existing: true`, как описано ниже.

## systemd и права

Оставьте штатные `User=godhcp` и `Group=godhcp`. Дополнительные capabilities для DDNS не нужны. Пользователю нужны чтение keytab, доступ к Kerberos-конфигурации, запись в каталог БД и временный каталог. Обработчик создаёт собственный каталог билетов с правами 0700 и удаляет его после цикла. Билет, полученный администратором в интерактивной сессии, служба не использует.

При ручном редактировании YAML:

```bash
sudo -u godhcp test -r /etc/godhcp/dhcp-dns.keytab
sudo -u godhcp godhcp -validate -config /etc/godhcp/config.yml
systemctl reload godhcp
journalctl -u godhcp -f
```

Проверка `-validate` проверяет структуру настроек, но не доступность KDC/DNS или права в AD. При запуске с включённым DDNS отсутствие нужных программ считается ошибкой запуска. Веб-форма тоже проверяет наличие программ до сохранения. Если Samba ещё поднимается после загрузки, ошибки Kerberos/DNS повторяются в фоне и не останавливают DHCP. Не заменяйте пользователя службы на root для устранения ошибки доступа к ключу.

## Диагностика и восстановление

Ищите в журнале `ddns updated`, `ddns deleted`, `ddns update failed`, `ddns synchronization failed`. Проверьте DNS отдельно:

```bash
dig @dc01.example.org printer.hosts.example.org A
dig @dc01.example.org -x 192.0.2.10
dig @dc01.example.org _godhcp-owner.printer.hosts.example.org TXT
```

`NXRRSET`/`YXRRSET` обычно указывают на конфликт владения или уже существующие данные; `REFUSED` — на права DNS; ошибка входа Kerberos — на keytab, principal, realm, DNS или время. Не удаляйте существующие записи и метки вслепую. Если `samba_verify` включён, кроме DNS/Kerberos должен быть доступен DNS RPC Samba: endpoint mapper и динамический RPC-порт. Ошибка RPC не считается успешным обновлением.

База аренд содержит также идентификатор владельца и незавершённые DNS-операции. Включайте её в согласованную резервную копию. После перезапуска операции повторяются с прежними метками. Потеря БД не позволяет новой БД автоматически управлять старыми метками; восстановите резервную копию или выполните проверенную ручную миграцию.

Отключение DDNS останавливает и обновления, и очистку. Изменение сервера/зон не удаляет записи в прежней области. Перед миграцией спланируйте их очистку. A и PTR изменяются отдельными DNS-транзакциями, поэтому временное расхождение при сбое возможно. TTL ограничивается оставшимся сроком аренды, но истечение TTL очищает кеши, а не авторитетную запись: при недоступном DNS очистка произойдёт после восстановления связи.

## Воспроизводимый стенд

```bash
bash scripts/test-ddns-samba.sh
```

Скрипт создаёт одноразовый Samba AD в изолированной Docker-сети, без публикации портов и подключения к рабочему домену. Проверяет реальные GSS-TSIG-обновления от Linux-пользователя `godhcp`: A/PTR, продление, перезапуск обработчика с сохранённой БД, переименование, передачу IP другому клиенту, истечение, защиту чужой записи и PTR-only. Это тест DNS-интеграции; он не заменяет загрузку реального DC через systemd или проверку сетевых DHCP-пакетов.

Справочные материалы: [Samba: DHCP и DNS](https://wiki.samba.org/index.php/Configure_DHCP_to_update_DNS_records), [samba-tool](https://devel.samba.org/samba/docs/current/man-html/samba-tool.8.html), [BIND nsupdate](https://bind9.readthedocs.io/en/stable/manpages.html#nsupdate-dynamic-dns-update-utility), [RFC4702](https://www.rfc-editor.org/rfc/rfc4702.html).

## Обновление существующих записей и YXRRSET

Начиная с v0.1.11 настройка `ddns.adopt_existing: true` разрешает принять существующие A/PTR-записи без метки GoDHCP и заменить значения текущими данными активных аренд. Отсутствующие записи добавляются. После принятия запись получает метку владения и участвует в обычном продлении, переименовании и очистке после завершения аренды. Сначала сохраните резервную копию DNS-зон и базы аренд; согласуйте, кто обновляет имена - DHCP или сами клиенты.

В существующей секции DDNS включите:

```yaml
ddns:
  enabled: true
  adopt_existing: true
  update_a: true
  update_ptr: true
```

Это фрагмент, а не полный config.yml: сохраните сервер, зоны, Kerberos/keytab и остальные настройки. В панели: «Конфигурация» → «Динамический DNS · Samba AD» → «Принимать существующие A/PTR-записи под управление GoDHCP» → «Сохранить DDNS». Включите также обновления DNS и нужные типы записей.

Захват выполняется одной DNS-транзакцией только при отсутствии TXT-метки `_godhcp-owner` и CNAME. Метки другого GoDHCP, защищённые имена и дубликаты имён активных клиентов не обходятся. Меняется только выбранный тип A/PTR; остальные типы сохраняются. Права DNS в Samba должны разрешать изменение старой записи: флаг не обходит ACL. Несколько старых значений одного A/PTR заменяются одним актуальным значением аренды.

`YXRRSET` означает, что условие отсутствия DNS-данных не выполнено. В обычном режиме это может быть существующая A/PTR-запись; в режиме принятия - оставшаяся метка владения или CNAME, в том числе при одновременном обновлении другим процессом. Журнал сообщает `ddns ownership conflict; existing records preserved` и перечисляет условия отклонённого принятия. Для проверки конкретного имени запросите его A или PTR, CNAME и TXT под именем `_godhcp-owner.<имя записи>` у авторитетного сервера. Не удаляйте чужую метку вслепую. `REFUSED` указывает на отказ сервера. Состояние DHCP-аренд от отказа DNS не теряется.

`interval_seconds` задаёт паузу между проходами. Длительный проход может выйти за этот интервал и обработать весь список. `timeout_seconds` ограничивает отдельную команду DNS или Kerberos. GoDHCP сверяет до восьми имён одновременно. При обновлении обоих типов PTR клиента обрабатывается после его успешного A, а конфликт одного имени не задерживает PTR других клиентов.

## Подсети /22

Пул DHCP /22 обслуживается как единая IPv4-подсеть. Для PTR можно использовать четыре существующие обратные зоны /24. Например, для 192.168.116.0/22 перечислите в `reverse_zones` зоны `116.168.192.in-addr.arpa`, `117.168.192.in-addr.arpa`, `118.168.192.in-addr.arpa`, `119.168.192.in-addr.arpa`. Для каждого адреса выбирается наиболее специфичная подходящая зона. Эти зоны нужно предварительно создать в DNS и делегировать права сервисной учётной записи. Отдельная зона с текстом /22 не нужна; ошибка YXRRSET не связана с маской подсети. RFC2317 для нестандартной делегации не реализован.
